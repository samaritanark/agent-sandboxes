# S5 — Gateway

**Status:** started. A prototype of the gateway contract in §5.8.4 and the
credential behaviour in §5.9.3 ran on Envoy, with a Lua filter standing in for
the broker. A second round tested upstream TLS validation and streaming
(SSE) scrubbing, and a third built a Go `ext_proc` prototype of the broker's
data path (one hard-coded credential), a fourth HTTP upgrades, a fifth mTLS
re-origination, and a sixth the encrypted store, per-session CA issuance, and
broker start. Real WebSocket and SPDY framing, ECH, corporate-proxy chaining, the Go controller, and the
unprivileged-user and seccomp posture were not tested, so the exit criteria
are not met.

## Environment

- Envoy 1.40.2 (`envoy-1.40.2-linux-aarch_64`, a 100 MB BoringSSL build), run
  as root inside the gateway namespace `gwA` of the S1 topology (appliance VM:
  Ubuntu 24.04 arm64, nested on an Apple M6, Lima 2.3.0). The Envoy download was
  not checked against a vendor digest (the release lists none).
- Clients ran in the agent-side namespace `agA` with `curl` (HTTP/1.1 and
  HTTP/2) and `nc`, not in a Kata microVM; the microVM-to-gateway path was
  covered in S1.
- Test CA and leaf certificates were generated with `openssl` (P-256). The
  upstream was a small Python server in the VM root namespace
  (`10.201.1.1:9000`) that echoes request headers, can redirect with the token
  in `Location`, and reports server-side whether it received the real
  credential (`X-Authorized`).
- Config: one listener on the gateway link address with `tls_inspector` and
  three kinds of match: **intercept** (TLS terminated; HTTP connection manager;
  route rules; Lua filter), **passthrough** (`sni_dynamic_forward_proxy` plus
  `tcp_proxy`), and **no match** (connection closed).

## Findings that change the design

1. **Blocked CIDRs belong in nftables on the gateway namespace's output
   chain**, not in the proxy. It checks the address actually dialled, so the
   check-then-connect gap in §5.8.4 item 2 cannot occur. The gateway's DNS
   queries to the upstream resolver need an explicit exemption: my first rule
   set included the resolver's `/24` and would have blocked name resolution.
2. **The root namespace needs its own input filtering on the uplink
   interfaces.** Before this, nothing stopped a gateway-namespace process from
   reaching listeners in the VM root namespace through the uplink address. With
   an `iifname "up…" drop` rule (allowing only the test port) the gateway
   namespace could no longer reach the VM's `sshd` on port 22. I only tested
   after adding the rule, so the "before" state is by construction, not
   measured. §5.8.2 describes rules for the gateway namespace but not for the
   root side.
3. **A new namespace has no working resolver** (S1), confirmed again: the
   gateway namespace needs an explicit upstream resolver address, set here
   through `/etc/netns/<ns>/resolv.conf` (the VM's gvisor-tap-vsock gateway,
   `192.168.5.2`).
4. **Envoy's own wildcard matching is already single-label**, which matches the
   design's default. The explicit multi-label `**.` form (OQ-10) is not
   something Envoy provides; it would need generated `server_names` entries or a
   controller-side match.
5. **Authority-versus-SNI checking and credential logic need filter code.** A
   Lua filter was enough for the prototype; the design's `ext_proc` broker
   (§5.8.4 data plane note) will take its place and was not tested. Lua buffers
   whole bodies for scrubbing, so streamed responses (SSE) are untested and
   probably need the sliding-window approach already described in §5.9.3.
6. **Per-session cost is small:** about 65 MiB and 0.1 s per gateway process.
   With one namespace per session, the "process per session or per namespace"
   question in §8 resolves to the same thing; six sessions would be about
   400 MiB of gateway memory, which should go into P-24.
7. **Passthrough is effectively free here**, so intercepting only the
   destinations that need L7 or credentials (§5.8.4 item 4) is a performance
   choice that costs nothing to keep.

## Second round: upstream TLS validation and streaming

Same VM and namespace; a second Envoy instance with plain-HTTP listeners on
the gateway's loopback and three upstream TLS servers in the root namespace
(a certificate for the right name from the test CA; one for a wrong name from
the same CA; one for the right name from an untrusted CA).

**Upstream TLS (what Envoy checks when it re-encrypts to the upstream):**

| Case | Result |
|---|---|
| Right name, trusted CA, subject-alternative-name matcher configured | HTTP 200 |
| **Wrong name**, valid certificate from the trusted CA, **no** SAN matcher | **HTTP 200: accepted** |
| Wrong name, trusted CA, SAN matcher configured | HTTP 503 (rejected) |
| Right name, **untrusted** CA, SAN matcher configured | HTTP 503 (rejected) |

Envoy validated the certificate chain but not the host name unless a
`match_typed_subject_alt_names` entry was configured. The controller must emit
an explicit SAN match for every intercepted upstream. (For dynamically
resolved hosts, Envoy's `auto_sni` plus `auto_san_validation` is the likely
equivalent; I did not test it.) System roots and the corporate CA bundle were
not used here; the test CA stood in for them.

**Streaming response scrubbing (SSE, five events one second apart; one event
carrying the real token):**

| Scrubber | First byte | Real token reaching the guest |
|---|---|---|
| None | 0.0006 s | yes (expected) |
| Lua `body()`, buffers the whole body | **5.0 s** (the end of the stream) | no |
| Lua that skips `text/event-stream` | 0.0007 s | **yes** |
| Lua `bodyChunks()`, per chunk, no hold-back | 0.0007 s | whole token in one chunk: scrubbed; **token split across two chunks 0.4 s apart: leaked** |

Buffering breaks live streaming, which is how model APIs return responses;
skipping streams leaks; chunk-wise scrubbing without a hold-back leaks any token
that straddles a chunk boundary. A scrubber that works for streams must keep the
last `len(token) - 1` bytes of each chunk back until the next chunk arrives and
flush them at end of stream, which needs state per connection: the `ext_proc`
streamed mode, not Lua. Not tested: the encodings from §5.9.3 (base64,
URL-encoding, the basic-auth pair), only the exact value.

Harness note: in both rounds the first one or two requests after starting a
test upstream failed with an Envoy connect failure although `nc -z` to the
same port had just succeeded; later requests worked. I did not find the cause,
and it did not recur once the upstream had been up for a few seconds, so
tests wait and retry.

## Third round: a Go `ext_proc` prototype of the broker's data path

About 170 lines of Go (`go-control-plane` v1.40, gRPC 1.85), cross-compiled for
linux/arm64 (19 MB), run in the gateway namespace on the loopback address,
behind a third Envoy instance with the `ext_proc` filter
(`failure_mode_allow: false`, response bodies in `STREAMED` mode). It holds one
hard-coded credential and placeholder; there is no encrypted store, rate
limiting, per-credential binding table, or token adapter.

| Behaviour | Result |
|---|---|
| Placeholder to the bound host: real credential injected | **Pass.** The upstream reported `x-authorized: yes` |
| Guest-supplied non-placeholder `Authorization` to the bound host | **Pass.** Removed; the upstream saw none |
| Placeholder to an unbound host | **Pass.** HTTP 403, `credential_misuse` logged with the correct authority |
| Real value in a reflected response header, a redirect `Location`, and a JSON body | **Pass.** None reached the guest |
| SSE with a whole token in one chunk and a token split across two chunks 0.4 s apart | **Pass.** Events arrived at their original times (0.00, 0.50, 1.00, 1.40, 1.90 s); both tokens were replaced; no fragment of the real value reached the guest |
| Added latency per request (300 sequential `GET`s, new connection each) | about 0.7 ms (2.88 ms against 2.15 ms direct to the upstream) |
| Broker memory | 16 MiB resident |
| **Fail closed** with the broker stopped | **Pass.** HTTP 500 for requests with and without a credential; nothing was forwarded |

How the streaming scrub works: the broker keeps, between chunks of one
response, only a suffix of the data that is a proper prefix of the real value,
because only those bytes could be the start of a token split across chunks.
That is usually zero bytes, so ordinary events are not delayed. A
fixed hold-back of `len(value) - 1` bytes would delay the end of every event
(the blank line that terminates it) until the next event arrived.

Pitfalls found while building it:
- **`StreamedBodyResponse` belongs to `FULL_DUPLEX_STREAMED` mode.** In the
  plain `STREAMED` mode I configured, the body must be returned as a per-chunk
  `body` mutation. Returning the other form was **silently ignored**: the
  response went through unmodified and the real token reached the guest, while
  the broker logged that it had scrubbed it. N-04 must read what the guest
  actually receives, not the broker's log.
- Envoy logged `Spurious response message 4 received on gRPC stream` for the
  wrong form; treat that line as an alarm in the gateway's own health checks.
- Response headers are mutated separately from bodies; removing
  `content-length` is needed whenever the body length can change.
- My first overhead measurement (6.2 ms) was taken while body scrubbing was
  silently not working, so it measured the wrong thing.

## Fourth round: HTTP upgrades

Same gateway namespace and `ext_proc` broker; two Envoy listeners that differ
only in whether the connection manager has `upgrade_configs` for `websocket`
and `SPDY/3.1`. The test upstream accepts a raw `Upgrade: websocket` handshake,
replies `101`, reports every `Authorization` header it received, pushes the real
token onto the tunnel, and echoes bytes. This tests the handshake and the
tunnel, not real WebSocket framing or SPDY.

| Case | Result |
|---|---|
| Upgrades not enabled (the default) | **HTTP 403** from Envoy; the connection is reset; nothing reaches the upstream |
| Upgrades enabled, placeholder in `Authorization` | `101 Switching Protocols`; the upstream saw exactly one `Authorization` header and reported `authorized=yes` (the real value was injected on the upgrade request) |
| Real token pushed by the upstream onto the upgraded stream | **Scrubbed**: the guest received the placeholder |
| Bytes sent through the tunnel | Echoed |

So the HTTP filter chain, including `ext_proc`, keeps processing the data of an
upgraded connection: credential injection happens on the upgrade request and
the response scrub applies to the stream afterwards. Not tested: real WebSocket
frames (a token inside a compressed `permessage-deflate` frame would not match
the plain-text scan, so negotiating that extension would need to be refused),
SPDY or `kubectl exec` streams, tokens split across frames, and the
request-direction stream.

## Fifth round: mTLS client-certificate re-origination (D-28, P-08)

A TLS upstream in the root namespace that requires a client certificate signed
by the test CA and records the client's common name and the server name it was
asked for. An Envoy cluster held the client certificate and key and set an
explicit `sni` (`kube.example.test`) different from the address it connected
to; the guest holds neither.

| Case | Result |
|---|---|
| Cluster with the client certificate and `sni: kube.example.test` | **Pass.** The upstream saw `client_cn=sbx-gateway-client` and `sni=kube.example.test`, with the server certificate validated by name |
| Same cluster without the client certificate | HTTP 503 (the upstream refused the handshake) |

This is the Teleport-style shape (a client certificate plus a TLS server name
that differs from the connect address). Not tested: a kubeconfig-derived
certificate, rotation, key storage in the broker (§5.9.2), and the API-server
deny-list (§5.9.5).

## Sixth round: encrypted store, per-session CA, and broker start (§5.9.2, §5.10)

A single Go program (`sbxcred`, about 520 lines on top of the `ext_proc` code,
linux/arm64, 20 MB) stood in for `sandboxd`'s credential duties:
`init-ca`, `store-put`, `session-start` (decrypt only the bound credentials,
mint certificates, start the broker as an unprivileged user), and the broker
itself with a binding table read from stdin (host, placeholder, secret,
injection method) instead of hard-coded values. Three credentials were stored;
sessions A and B each bound a different subset.

**Encrypted store (AES-256-GCM, credential id as associated data):**

| Check | Result |
|---|---|
| Plaintext secrets found in the store directory | 0 files |
| One flipped byte; wrong key; an entry moved under another id | all **rejected** at decryption |
| Unprivileged gateway user reading the store key, a store entry, or the CA key | `Permission denied` for each; the public root certificate is readable |

**Handover and memory (a python scan of `/proc/<pid>/mem`):**

| Check | Result |
|---|---|
| Broker runs as the unprivileged user | yes (`sbxgw`); parent was the root helper |
| Secrets in the broker's command line, environment, or any file under the runtime directory | none (secrets arrive over a stdin pipe only) |
| Secrets in session A's broker memory (A binds two of three credentials) | the two bound secrets present, the third **absent** |
| Secrets in session B's broker memory (B binds only the third) | only the third present |
| Secrets in the **long-lived root helper's** memory after it handed over and zeroed its buffers | **still present**: Go strings are immutable and cannot be wiped |
| Same, with the helper run detached (`--detach`: decrypt, start the broker in its own session, exit) | the helper is gone; the broker was reparented to init and kept serving |
| Other processes whose memory held the real value after requests flowed | Envoy (the injection point; expected, §5.8.2) and, as test artifacts, the SSH session and shell that carried my script text and a test upstream whose source contains the value |

**Certificates (per-session intermediate, 2 h validity, `pathlen:0`,
name-constrained and marked critical to that session's hosts):**

| Check | Result |
|---|---|
| A guest that trusts only the install root verifies the chain Envoy serves | **Pass** (`Verification: OK`) |
| Injection end to end: bearer token for one host, a custom header for another | **Pass** (`x-authorized: yes`, `x-authorized-other: yes`); no secret reached the guest |
| A placeholder sent to a host it is not bound to | **403** |
| Leaf for the permitted name or a subdomain of it, signed by session A's intermediate | verifies |
| Leaf for `evil.com` signed by session A's intermediate | **rejected** by OpenSSL: `permitted subtree violation` |
| Session B's intermediate signing a leaf for session A's host | **rejected** the same way |
| Gateway user reading the leaf key / the intermediate key / the root key | readable (needed to serve TLS) / denied / denied |
| After teardown (broker killed, session directory removed) | the broker is gone and a request with A's placeholder returns HTTP 500 (fail closed) |

Findings:
- **The decrypt-and-start step must be a short-lived helper.** A long-lived
  root process cannot clear a Go string, so it would accumulate every session's
  plaintext. Running the step as a process that exits after the handover left
  the plaintext only in the broker (and, transiently, the gateway). `sandboxd`
  then supervises a reparented broker by cgroup or transient unit, not as a
  child process, which the design does not yet say.
- **Handover bug worth remembering:** zeroing the secret buffer right after
  starting the process corrupted the table, because `exec.Cmd` copies a
  stdin reader to the pipe asynchronously; the helper must write the pipe
  synchronously and only then wipe.
- **Leaves are minted per host at session start**, so the gateway never needs
  the intermediate key; a hot-added intercepted name needs the root helper to
  issue another leaf. The prototype kept the intermediate key on disk (root,
  0600) only so the tests could model a compromised issuer; the design should
  not store it.
- **Revocation is by expiry and teardown only.** The certificates stay valid
  until their end time (2 h here); nothing revokes them, so a stolen leaf key
  is usable for the session's lifetime against the guest's trust root.
- Not tested in this round: key push from the host keychain, rate limits and
  quotas, signed bindings, per-credential audit events, and the
  token-endpoint adapters. Enforcement by the guests' TLS stacks is the
  seventh round.

## Seventh round: do the guests' TLS stacks enforce name constraints?

Each client trusted only the test root and connected to three local TLS
servers: a leaf for `api.test.local` signed by a name-constrained intermediate
(critical, `pathlen:0`, permitted `DNS:api.test.local`); a leaf for `evil.com`
signed by the same intermediate; and, as a control, a leaf for `evil.com` signed
by an **unconstrained** intermediate. A stack is correct only if it accepts the
first, rejects the second, and accepts the third (which shows the test can see
a client that ignores the constraint). Ubuntu 24.04 arm64 in the VM.

| Client (TLS library) | Permitted name | `evil.com`, constrained CA | `evil.com`, control |
|---|---|---|---|
| `openssl s_client` (OpenSSL 3.0.13) | accepted | **rejected** | accepted |
| `curl` 8.5.0 (OpenSSL 3.0.13) | accepted | **rejected** | accepted |
| Python 3 `ssl` (OpenSSL 3.0.13) | accepted | **rejected** | accepted |
| Node 18.19.1 `tls` (bundled OpenSSL 3.0.13) | accepted | **rejected** | accepted |
| `wget` 1.21.4 (OpenSSL) | accepted | **rejected** | accepted |
| `git` over HTTPS (libcurl-gnutls, **GnuTLS**) | accepted | **rejected** | accepted |
| Go `crypto/tls` (Go's own `crypto/x509`, Go 1.27) | accepted | **rejected** | accepted |

All seven behaved correctly, which covers OpenSSL, GnuTLS, and Go's
independent implementation. Not tested: rustls/webpki (the Rust agents'
likely stack; no Rust toolchain here), BoringSSL (browser-class dependencies),
Java, and the agents' own bundled runtimes, which may carry their own trust
logic. Two harness notes: my first `wget` run was invalid (it connected by
IP, so it failed hostname checks even for the control), and `git` was checked
by whether its error mentioned certificate verification.

- More than one session, and a Linux host.

## Harness notes

Two harness mistakes cost time and are recorded because they will recur:
processes started with `nohup … &` in one SSH session did not survive the
session ending (`setsid -f` did), and truncating a log file that Envoy still
held open left the file starting with NUL bytes, so `wc -l` undercounted its
lines.
