# S8 — Policy-layer port pilot

**Status:** pilots 1 to 4 done (branches `s8-go-port`, merged to `v3`, and
`s8-secret-gate`): `finding_is_encrypted` (about 130 lines of bash);
`is_path_masked`, `extract_yaml_list_from_file`, and `_leakscan_finding_accepted`
(pilot 2); `scan_repo_secrets` with the helpers it owns (pilot 3); and
`secret_gate_repos` (pilot 4), which completes the secret gate. Each is ported
with a differential harness, a mutation-tested corpus, and a live Linux oracle.
Pilots 5 to 9 port all of `lib/vetting.sh` (`go/internal/vetting`): posture and
configuration, repo classification and signed-tag verification, the drift decision
and the launch gate, the committed-exception readers and signing-key state, and
attestation (signing, exception acknowledgment, the inline attest, signing setup).
The rest of the policy layer (config, checks, link, audit, onboard, agents, catalogue,
profile, credentials, and the CLI) is not ported, so the exit criteria are not met.

## Pilot 1: `finding_is_encrypted` (2026-11-18)

**What was built** (module `github.com/samaritanark/agent-sandboxes/go`, branch
`s8-go-port`, Go 1.27 toolchain, `go 1.24` in `go.mod`):
- `go/internal/gate/encrypted.go`, 295 lines: a literal port of the 134-line
  bash function, including its awk logic (SOPS envelope containment and a YAML
  walker for Bitnami SealedSecrets). Positions are bytes.
- `encrypted_test.go`, 206 lines: the bash suite's own assertions, a golden
  comparison, and a live-oracle test (`SBX_ORACLE=1`, Linux only; in CI it fails
  if not enabled rather than skipping).
- `internal/gencorpus`, 368 lines: a seeded corpus generator.
- Test data, about 2 MB: 10 fixtures extracted by name from
  `tests/test-secret-gate.sh`, 8 hand-written adversarial files, 1,000 seeded
  mutants of those, and 35,057 (file, line, startcol, endcol) cases.

**Method.** The bash oracle runs on Linux, not macOS, because the appliance's
`awk` is not macOS's. Its answers are stored as golden files; the live-oracle
test re-runs the bash from inside the Go test (34 s for all cases) so a golden
file cannot go stale. Mutations: indentation and dedent, blank and comment
lines, deleted, duplicated, and swapped lines and blocks, CRLF, missing final
newline, tabs (leading, after the colon, after a list marker), document
separators, `kind` and `apiVersion` variants, damaged envelopes, multibyte
characters, list-marker prefixes, whole-file wrapping as a Helm `extraObjects`
element, and concatenation with another fixture.

**Results**
- The 17 assertions that mirror the bash suite passed on the first run.
- **0 divergences** from the oracle on all 35,057 cases (553 fixture cases, 34,504
  mutant cases), under `gawk` 5.2.1 with `LC_ALL=C`.
- **Mutation testing of the corpus.** I planted 22 bugs in the port to check
  that the corpus could see them. The first, random-only corpus caught 5 of 9;
  after adding the adversarial files and block-swap, concatenation, tab, shift,
  and wrap mutations, **17 of 22** were caught. The 5 not caught were examined:
  four cannot change any output (a `#`-first-key regex whose case is already
  handled as a blank line; a trailing-newline record that yields the same
  answer; a blank-target check reached by another branch; an `ENC[` restart that
  cannot overlap itself), and one was my own invalid trial (it replaced a comment, not
  the regex) which, redone correctly, was caught.

**Findings about the v2 bash (the oracle)**
1. **Its answers depend on the awk implementation and the locale.** On the
   VM, `awk` is GNU awk 5.2.1 and `LANG` is `C.UTF-8`. `mawk` 1.3.4 gave
   identical answers in both locales (0 of 34,504 differ); `gawk` in `C.UTF-8`
   differed on 12 cases, all on lines with multibyte characters before the
   envelope, because it counts characters. The Ubuntu default `awk` is `mawk`; the
   VM has `gawk` (I did not find why, but installing QEMU earlier is one candidate), so the
   appliance image's package set decides this and should be pinned.
2. **betterleaks reports byte columns** (1.10.0: for `é日本語 token: ...` it
   reported StartColumn 20, the byte offset, where the character offset is 13).
   So byte positions, which the port uses, are correct, and the v2 bash on the
   VM's default `gawk` + `C.UTF-8` is wrong on those lines. This is a place
   where the port is more correct than the original; it is also a behaviour
   difference from the oracle in that one environment, and I made it
   deliberately.
3. **The gate's documented column convention does not match betterleaks 1.10.0.**
   The comment and the test helper `colspan_of` assume betterleaks reports
   StartColumn one past the real start, and the gate lowers the start by one
   before comparing. **Correction (same day, after the fixes work):** my first
   measurement here was wrong. I used a token one character longer than the
   scanner's rule matches, so EndColumn looked one short. Re-measured with a
   token exactly as long as the match, on five shapes (line start, middle, quoted,
   inside an `ENC[...]` envelope, after multibyte text), betterleaks 1.10.0 reports
   exact 1-based inclusive byte columns for both ends. The gate's start
   adjustment is therefore one column too strict at the start, and correct at the
   end; with real envelopes (which begin `ENC[AES256_GCM,`) it has no practical
   effect. It is fixed in the port (deviation `ExactColumns`).

**Effort data for the estimate.** Porting this unit took one working session
including the harness, the corpus generator, the mutation testing, and the
findings above. The harness, corpus generator, oracle runner, and golden
workflow are reusable for every later unit, so the next units should cost
mainly the port itself. The gate's other units are larger and touch git,
`betterleaks`, and the filesystem, so they need a stub scanner and fixture
repositories, not just text files. I would not extrapolate a total from one
pure function.

**Open questions raised**
- Which `awk` and locale does the appliance image guarantee? The Go port makes
  this moot for ported units, but the bash oracle's own goldens depend on it, so
  the golden files record `gawk` 5.2.1 and `LC_ALL=C`.
- (Answered: corrected in the port as the `ExactColumns` deviation.)

## Pilot 2: path masks, YAML list reader, accepted-finding check (2026-11-18)

**What was built** (`go/internal/gate`): `masked.go` (`IsPathMasked`,
`ExtractYAMLList`), `accepted.go` (`LeakscanFindingAccepted`), their tests, a
config/case generator (`internal/genmasked`), and fixtures: 323 config files
(23 hand-written, 300 seeded random compositions of fragments, with CRLF and
missing-final-newline variants), 40,126 (config, path) cases, and a git fixture
for the accepted-finding check (tracked, untracked, and ignored files; 15
ignore-file variants; 33 relpaths including git pathspec magic such as `d*`,
`:(top)a.txt`, `:!a.txt`, `../a.txt`; 2,475 cases). `LeakscanFindingAccepted`
runs the same `git ls-files --error-unmatch` as the bash, so it needs git at run
time.

**Results**
- **0 divergences** from the oracle on `is_path_masked` (40,126 cases),
  `extract_yaml_list_from_file` (323 configs, 1,457 items), and
  `_leakscan_finding_accepted` (2,475 cases). Oracle: gawk 5.2.1, git on the
  VM, `LC_ALL=C`.
- **Mutation testing.** I planted 23 bugs in the two new files. The first
  corpus caught 20; both survivors were corpus gaps and are now caught after
  adding a near-miss suffix (`openrc.sh`, `x_openrc.sh`) and column-0 `-n` list
  lines. A third survivor (`acceptFile == ""`) is equivalent: `os.Stat("")`
  fails anyway.
- **Oracle bug caught by the harness itself.** My first oracle script sourced
  only `lib/filesystem.sh`. `load_repo_masked_paths` lives in `lib/config.sh`,
  so the bash silently treated every repo's `masked_paths:` as empty and the
  first run showed 2,304 "divergences" that were in fact the oracle being
  wrong. The oracle script now fails loudly if that function is undefined.
  Lesson for later units: an oracle that cannot call the function should abort,
  not return "no".

**Findings about the v2 bash**
1. **A `masked_paths:` entry that is `-n`, `-e`, `-E`, or a combination of those
   cannot be masked.** `extract_yaml_list_from_file` passes each line through
   the `echo` builtin, which reads such a word as an option and prints nothing.
   It happens twice: on the raw list line when it starts in column 0 (`-n`), and
   on the final item (`- -n`). Practical impact is small (a file literally named
   `n`, `e`, or `-n`), and the port keeps it. It is also an example of the
   class of bug Go removes.
2. **`masked_paths:` is matched literally.** Glob characters in an entry (`*.pem`,
   `secrets/*`) mask nothing; only exact paths and trailing-slash directories
   work. This is probably known, but the gate's comments do not say so. The port
   keeps it.
3. **`_leakscan_finding_accepted` treats `relpath` as a git pathspec.** A
   fingerprint line for `d*` or `dir` is accepted if any tracked file matches
   the pathspec, even though the finding's real path is something else. The ignore
   file is repo-controlled, so a fingerprint naming a path that matches a tracked
   file is within what the file already controls; but the tracked-file gate is
   weaker than its comment ("the file is git-tracked") suggests. Not changed in
   the port. Whether to use `:(literal)` is a separate, reviewed change.
4. Newlines inside arguments, and NUL bytes in files, are not covered by either
   corpus.

**Not done:** the live-oracle tests for pilot 2 (`TestMaskedLiveOracle`,
`TestAcceptedLiveOracle`) are written but have not been run: the VM has no Go
toolchain, and they need Linux. The goldens were generated on the VM by the same
oracle scripts. `awk` is not used by these units except in `extract_yaml_list_from_file`
(mawk was not compared for it).

## Pilot 3: `scan_repo_secrets` and its helpers (2026-11-18)

**What was built** (`go/internal/gate/scan.go`, about 660 lines): the scan
entry point plus `_leakscan_operator_config`, `_leakscan_ignore_path`,
`_leakscan_write_config`, `_betterleaks_run`, the exclusion and inline-allow
switches, `resolve_overlay_path`, `extract_yaml_scalar_from_file`,
`strip_ignore_file_comments`, and a bash-glob matcher for the dependency-dir
names. The scanner stays an external process: the port runs the same
`nice`/`ionice`/`betterleaks dir ...` command line and parses the same JSON
report. The `jq` filters are replaced by a decoder that mimics jq's behaviour
(`@tsv` escaping, `tostring`, per-value error handling, multi-value streams) and
by an emulation of `IFS=$'\t' read`, which collapses empty fields.

**Method.** A stub `betterleaks` (`testdata/scan/stub`) answers from a scenario
directory and logs its argument list, the generated config's full text, and
whether `-i` is an empty directory. Both the bash and the Go side run against
the same fixture tree (`setup.sh`: 13 repos including symlinked and
`.git/config`-less ones, 13 overlays, 7 user configs, 3 accept files). The
compared output is the gate's stdout plus the stub's log, so a divergence in the
generated config, the flags, or the fail-closed paths shows up as well as one in
the classification. 273 scenarios (hand-written plus 250 seeded random reports:
malformed JSON, streams, non-object elements, null and missing fields, tabs,
newlines, backslashes, multibyte text, out-of-repo and prefix-confusable paths,
`.git/` paths) are run in 1,033 (scenario, environment) cases.

**Results**
- **0 divergences** on 1,033 cases (gawk 5.2.1, jq 1.7, git, `LC_ALL=C`). The
  golden covers 236 `sealed`, 218 `yes`, 47 `accepted`, 1,573 `no`, 807
  `gitconfig`, and 431 `error` lines, including every fail-closed message.
- **Mutation testing.** About 40 bugs planted in `scan.go`. Every survivor was
  examined: seven are equivalent or cannot be observed through the stub (an
  `-z file` guard that is unreachable because of the read quirk below; resolving
  the config from the real path instead of the symlink, which is the same
  directory; stripping one versus all trailing slashes from `git` output; a
  trailing-tab trim that `@tsv` escaping makes moot; an empty-report check that
  another check covers; the `ionice` class and the exit code for a missing
  `nice`, which the stub never sees). One was a real corpus gap, tilde expansion
  of the overlay path, closed by pointing the fixture's extra dependency
  directory at it. Two further trials were invalid (a no-op edit, a pattern typo).

**Findings about the v2 bash**
1. **`[[ -z "${file}" ]] && continue` cannot do its job.** `IFS=$'\t' read`
   treats tab as whitespace, so a finding with an empty `File` loses its leading
   field: the rule ID becomes the file, the line becomes the rule, and so on. The
   gate then classifies a shifted record. betterleaks always fills `File`, so
   this is latent; the port reproduces it.
2. **Non-ASCII directory names are never excluded from the scan.** `git ls-files`
   prints them C-quoted (`"\303\274n\303\257/.venv/"`), the quote defeats the
   basename match, and the generated allowlist omits them. This fails safe (the
   directory is scanned), at the cost of walking it. Fixture `ünï/.venv`
   demonstrates it.
3. **Relative-path stripping treats the repo path as a glob.**
   `${file#${real_repo}/}` is an unquoted pattern, so a repo path containing `*`,
   `?`, or `[` would strip the wrong prefix. The port strips literally; the corpus
   does not cover repo paths with glob characters.
4. **The gate trusts the scanner's report shape.** A report whose last JSON
   value is an array passes the fail-closed check even if earlier values in the
   stream are not (`jq -e` looks at the last output). The scanner does not emit
   streams, so this is theoretical; the port matches it.

**Not done:** the live-oracle test (`TestScanLiveOracle`) is written but not run
(no Go on the VM). Not covered: non-integer JSON numbers, nested values inside
`StartLine` and the column fields, NUL bytes, repo paths containing glob
characters, signal exit codes, the `nice` and `ionice` arguments (the stub only
sees what follows them), and the real betterleaks (the stub replaces it, so
nothing here checks what the scanner finds).

## Pilot 4: `secret_gate_repos` (2026-11-18)

**What was built** (`go/internal/gate/secretgate.go`, about 350 lines): the launch
gate itself: the per-repo loop, the four outcomes (flag override, trusted-endpoint
prompt, no-terminal refusal, hard refusal), the findings and remediation
messages, a port of bash's `printf '%q'`, and the `SESSION_SECRET_SUMMARY` and
override records. It takes its neighbours as injected functions
(`vetted_accepted_fingerprints`, `vetting_exceptions_from_commit`,
`record_override`, `load_repo_accepted_secrets`, `warn`, the terminal), because
vetting and audit are later units.

**Method.** The oracle wraps the real function with mocks for those neighbours
that log their calls, runs it against the stub scanner and the pilot-3 fixture
repos, and records stdout, stderr, the mock call log, the stub's log, the exit
status, and `SESSION_SECRET_SUMMARY`. The prompt path runs on a pseudo-terminal
(`ptyrun.py`, echo and output post-processing off) with each reply typed or an
end-of-file sent; those cases compare the combined stream. 393 cases over 75
scenarios: the full flag matrix on seven scenarios, 54 prompt cases (replies `y`,
`Y`, `yes please`, `n`, empty, EOF, `x`, ` y`, `\y`), odd flag values, 1 to 3
repos including symlinked and duplicate ones, per-repo scanner answers, a
retired `accepted_secrets:` list, scanner failure on one repo among several,
missing `betterleaks`, and about 30 awkward file names (spaces, quotes, `$`,
`~`, `#`, control characters, multibyte, zero-width characters).

**Results**
- **0 divergences** on 393 cases (bash 5.2.21, `LC_ALL=C.UTF-8`). The golden
  holds 259 refusals, 134 passes, 72 flag override records, 16 accepted prompts, and
  20 aborted ones.
- **Mutation testing.** About 20 planted bugs. Two survivors are equivalent (an
  empty-`relpath` guard that the read quirk below makes unreachable; temp-file
  cleanup and an unset summary on the error exit, neither observable). Two real
  corpus gaps (the flag compared with `!= "false"`, and the trusted-endpoint test
  loosened) were closed by adding odd flag values and prompt cases with them.

**Findings about the v2 bash**
1. **`sandbox mask add --repo <repo>` is printed with the repo path unquoted**,
   while the file arguments are `%q`-quoted. A workspace path containing a space
   or shell metacharacter gives a command that cannot be pasted. Usability, not
   security. The port keeps it.
2. **The remediation commands depend on the locale.** `printf %q` prints
   non-ASCII file names literally in a UTF-8 locale and as `$'\303\251'` in the
   C locale. Both are valid shell. The port implements the UTF-8 behaviour; a
   non-printable-character table that differs from glibc's (unassigned code
   points) is not covered.
3. **Only the literal string `true` counts for `--i-accept-unmasked-secrets` and
   for the trusted endpoint.** `yes`, `TRUE`, and an empty value mean no. That is
   the safe direction, and the caller passes `true` or `false`; recorded here so
   the Go CLI does not widen it.
4. **A reply with surrounding whitespace is accepted** (` y`): `read` trims it.
   `\y` is refused.
5. **The empty-`relpath` check in the loop cannot fire** (same `read` collapse as
   pilot 3, finding 1).

**Not done:** the live-oracle test (`TestGateLiveOracle`) is written but not
run (no Go on the VM). The mocks stand in for vetting and audit, so nothing here
tests that the gate and those modules agree on the accept-file contents or on
what `record_override` stores. Not covered: a failing `vetted_accepted_fingerprints`
(the bash swallows it), the real `warn`, and terminals other than a pty.

## Pilot 5: vetting posture and configuration (2026-11-18)

**What was built** (`go/internal/vetting/config.go`, about 280 lines):
`resolve_vetting_posture`, `vetting_max_commits_behind`, `vetting_max_age_days`,
`_vetting_age_days`, the four tighten-only switches
(`vetting_exceptions_require_head`, `_require_clean_worktree`,
`_exceptions_from_commit`, `_forbid_unvetted_override`), `vetting_trust_root`
and `vetting_trust_roots`, `vetting_trust_format`, `vetting_signing_key`, and
`_vetting_extract_signer`. It reuses the overlay and YAML helpers from package
`gate`; they move to a shared package when the module layout is settled (§5.1.1).

**Method.** 140 user and 90 overlay configs (random subsets of the ten keys with
values drawn from pools of well-formed, malformed, quoted, commented, and
zero-padded or oversized numbers, plus indented and duplicate keys), combined into
1,102 cases against two home directories (with and without the default trust
root), plus 19 timestamps for the age function against a fixed clock (a `date`
shim in the oracle) and 28 `git tag -v` outputs for the signer parser. Each case
records every function's output and any `WARN:` line. The bash's own
arithmetic-error messages on stderr are not compared.

**Results**
- **0 divergences** on 1,104 case groups (bash 5.2.21, `LC_ALL=C`). The golden
  holds 149 warnings, 58 `off` and 85 `required` postures, 70 cases with two trust
  roots, and 204 with `gpg`.
- **Mutation testing.** 21 planted bugs, 18 caught. The 3 survivors are
  equivalent (an unreachable default in the rank table, `>` versus `>=` between
  equal ranks, `>` versus `>=` when the timestamp equals now).

**Findings about the v2 bash**
1. **The "most restrictive cap wins" rule can be defeated by a zero-padded value.**
   The comparison is `[[ v -lt eff ]]`, which is arithmetic: a leading zero means
   octal, and `08` or `09` is an arithmetic error that makes the test false. If
   the user sets `vetting_max_commits_behind: 08` and the overlay sets `5`, the
   first value is accepted unconditionally and `5 -lt 08` errors, so the effective
   cap is `08` (8 or an error downstream), looser than the overlay's 5. In the
   other order the overlay's 5 wins. Same for `vetting_max_age_days`. An overlay
   cannot rely on being the tighter bound if a user config can be edited by
   someone who knows this; whether that matters depends on who writes the user
   config. The port reproduces it and a fix (reject values that are not plain
   decimal) is a separate, reviewed change.
2. **Zero-padded valid octal is read as octal.** `010` compares as 8 but is
   returned as the string `010`, so a consumer that compares it as a decimal
   string and one that uses arithmetic disagree.
3. **Very large values wrap.** `9223372036854775808` becomes -2^63 and
   `18446744073709551616` becomes 0, so both look like the strictest possible cap.
   They fail toward "refuse", which is the safe direction.
4. **`vetting_signing_key` is deliberately user-only**, while the trust format is
   user-then-overlay; the port keeps the split.

**Not done:** `TestConfigLiveOracle` is written but not run (no Go on the VM). The
bash's arithmetic error text on stderr is not reproduced. Out of scope for this
pilot: everything that calls git or checks a signature (`_vetting_git`,
`vetting_status_repo`, the drift decision, the gate, attestation).

## Pilot 6: vetting verification: `_vetting_git`, `_vetting_verify_tag`, `vetting_status_repo` (2026-11-18)

**What was built** (`go/internal/vetting/verify.go`, about 250 lines): the git
wrapper that neutralizes an untrusted workspace's config, the single-tag signature
check with every verifier program pinned, and the classifier that picks the
freshest verified ancestor attestation and prints the one TSV line the gate reads.

**Method.** `setup.sh` builds 22 git repositories (plus a symlink and a plain directory) with fixed dates (so commit
hashes, tag dates, and distances are reproducible) and three throwaway SSH keys:
no tag, empty, shallow clone, tag at HEAD, tags 1 and 3 commits behind, several
tags where the freshest verifies, ties between tags at one commit (names chosen to
sort differently in different locales), a divergent branch, a tag signed by an
untrusted key, unsigned and lightweight tags, wrong prefixes, odd tag names, a
branch named like a tag, dirty trees (untracked, modified, staged), a symlinked
path, a path that is not a repository, and **a hostile workspace**: its own
`.git/config` names scripts for `gpg.ssh.program`, `gpg.program`,
`gpg.x509.program`, `core.fsmonitor`, `core.hooksPath`, and for content filters
(including a name containing `=`, an empty name, a name containing a dot, and one
defined through `[include]`), it sets `gpg.ssh.allowedSignersFile` to a file trusting
the attacker's key, and it carries a tag signed by that key plus tags whose
armor claims X.509 and OpenPGP. Every script leaves a marker file if it runs, and
the oracle records the markers after each case. 270 cases cross these repositories
with ten configuration and trust-root combinations (default root, a second root,
an overlay root, no root, GPG format, a missing root, clean-worktree required).
The same repositories are rebuilt on macOS and Linux, so the Go port's
verification (macOS `ssh-keygen`, git 2.56) is checked against the bash's (Ubuntu
`ssh-keygen`, git 2.43).

**Results**
- **0 divergences** on 270 cases (bash 5.2.21, `LC_ALL=C.UTF-8`): 68 vetted, 118
  unvetted, 6 dirty, 10 not-git, and 68 error lines.
- **No marker file was created in any case**, in the bash or in the port: none of
  the hostile workspace's programs ran, and its attacker-signed tag did not verify.
- **Mutation testing.** About 25 planted bugs. Removing any of these made the
  corpus fail: the `core.fsmonitor` pin, the filter-pin count, the filter-name
  regex (dotted names), the `gpg.ssh.program`, `gpg.program` and `gpg.x509.program`
  pins, the pinned `allowedSignersFile` in either mode, the clean-worktree check,
  the ancestor check, and the ordering. Survivors, examined: the `smudge` and
  `required` pins and the `clean` pin are not observable (see finding 1);
  `GNUPGHOME=<empty dir>` in ssh mode is not tested because that needs a real
  OpenPGP-signed tag and key; the `unknown` signer default and the digits check on
  the tag date cannot be reached with these fixtures.

**Findings about the v2 bash**
1. **The `process=` pin does most of the work for filters.** Pinning
   `filter.<name>.process` to the empty string makes git skip the filter's `clean`
   command too (a status over a hostile `*.txt filter=x` repository ran no `clean`
   script with only `process`, `smudge` and `required` pinned). The explicit
   `clean=cat` pin is therefore redundant on git 2.43 and 2.56. It is worth
   keeping as defence in depth; the Go port keeps all four pins.
2. **Which tag is reported can depend on the locale.** The freshest-first order is
   `sort -n -k1,1`, which breaks ties between tags at the same distance by
   locale collation. Under `en_US.UTF-8` punctuation sorts differently from the C
   locale, so two attestation tags at one commit can swap places. Vetted or not
   does not change (any verifying tag counts); the reported tag name and signer can.
   The port uses byte order, matching `C.UTF-8`.
3. **Verification on the operator's host runs `git tag -v` with real programs.**
   The pins hold in the cases above; what they cannot cover is a program the
   operator's own environment supplies (`GNUPGHOME`, `SSH_ASKPASS`) beyond what is
   pinned. Not tested.

**Not done:** `TestVerifyLiveOracle` is written but not run (no Go on the VM). Real
OpenPGP-signed tags are not covered (key generation under `gpg-agent`'s socket-path
limit differs between macOS and Linux temp directories), so GPG-format verification
and the empty-`GNUPGHOME` isolation in ssh mode are untested beyond "an SSH-signed
tag does not verify in gpg mode". A custom tag prefix and a very large repository
are not covered.

## Pilot 7: the vetting launch gate: `_vetting_drift_decision`, `vetting_gate_repos` (2026-11-18)

**What was built** (`go/internal/vetting/gate.go`, about 410 lines): the drift and
staleness decision, the gate's three postures, the per-repo loop, the interactive
attest offer, the override and refusal messages, and the audit summary string. The
gate's collaborators are injected: the status classifier, the configuration values,
audit, signing and inline attest, and the terminal.

**Method.** The oracle wraps the real function with a scripted
`vetting_status_repo` (one status line per repo per scenario), scripted
configuration, mocked audit and attest, and the real `_vetting_age_days` against a
fixed clock. 227 scenarios of one to three repos (random status lines: vetted at
varying distance, signer, and tag age, including future and malformed dates;
unvetted with and without a "no " reason; dirty; not-git; error; unknown status;
empty) and seven hand-built ones, in 2,796 cases: every posture and flag
combination on the hand scenarios with and without caps, 922 cases on a
pseudo-terminal answering one or several prompts (`y`, `n`, end of input, ` y`,
`Y`, `yes`, mixed), the attest offer with different signing and attest results,
the forbid-override policy, no trust root, and odd values for the posture, flags,
and caps (`08`, `010`, an overflowing number).

**Results**
- **0 divergences** on 2,796 cases (bash 5.2.21, `LC_ALL=C.UTF-8`). The golden
  holds 1,024 refusals and 1,772 passes, 211 drift and 215 unvetted override
  records, 185 accepted and 154 declined prompts, and 99 launches that attested
  inline.
- **Mutation testing.** About 25 planted bugs; every one that changes behaviour was
  caught (each flag test, the posture checks, the cap and age comparisons, the
  override-forbidden policy, the attest conditions, the prompt parsing). Three
  survivors are equivalent or dead code (finding 1).

**Findings about the v2 bash**
1. **Dead code: the "(N other(s) attested at launch)" suffix is never shown.** After
   the attest offer the gate appends it to a detail string, but that string is only
   used on the `--i-accept-unvetted-repo` path, which the attest offer excludes
   (`accept != true`). Harmless; the port keeps it so the diff stays literal.
2. **The gate evaluates its inputs as shell arithmetic.** `[[ "${behind}" -gt
   "${cap}" ]]` and its siblings treat a non-numeric operand as a variable name, so
   a status line carrying `abc` aborts the gate (`abc: unbound variable`, shown by
   a corpus run before I removed the unrealistic lines), and an operand shaped like
   `a[$(cmd)]` is the classic way to make shell arithmetic run a command (I did not
   exercise that here). In practice every operand is digit-checked
   upstream (`behind` by `vetting_status_repo`, the caps and age by their
   getters), so nothing reaches it; the Go port compares integers and has no such
   class. Zero-padded values (`08`, `010`) reach it and compare as the pilot-5
   findings describe.
3. **An unknown posture enforces unless there is no trust root.** `vetting_gate_repos`
   treats anything but `off` and `advisory` as required for drift and refusal, but
   the "no trust root" branch tests `== required`, so an unrecognised posture with
   no roots is let through as if advisory. Callers pass a normalized posture, so it
   is unreachable today; the port reproduces it.
4. **A tag date that fails the age check does not stop a launch.** An unreadable or
   non-numeric date yields an empty age and the staleness test is skipped, so a
   vetted repo with an unreadable tag date passes the recency cap. The status
   classifier only passes digits, so this needs a git failure on that one read.

**Not done:** `TestVettingGateLiveOracle` is written but not run (no Go on the VM).
The interactive paths are exercised with stdin and stdout both on a terminal; a
terminal on one only is not. The inline attest, the signing check, and audit are
mocks, so nothing here checks that they agree with the gate; they are the next
units (`vetting_attest_repo` and friends). The bash's arithmetic-error text on
stderr is dropped from the comparison.

## Pilot 8: committed-exception readers and signing-key state (2026-11-18)

**What was built** (`go/internal/vetting/exceptions.go`, about 175 lines):
`vetting_committed_ignore_fingerprints`, `vetting_committed_legacy_accepted_secrets`,
`vetting_committed_allowed_domains`, `vetted_repo_allowed_domains`,
`repo_granted_allowed_domains`, `vetted_accepted_fingerprints` (from
`lib/filesystem.sh`, the secret gate's accept-list source, previously mocked in
pilot 4), `load_repo_ignore_fingerprints`, `repo_ignore_file`, and
`_vetting_ssh_key_usable`, `_vetting_ssh_signingkey_state`,
`_vetting_signing_configured`.

**Method.** `setup.sh` builds 17 repositories with fixed dates and SSH-signed
tags: vetted with a different working-copy list, drifted by 1 and 3 commits (the
committed list changed after the tag), drifted and dirty, unvetted, only
`.gitleaksignore`, both files, an ignore file that is a directory, none, an ignore
file that is untracked or gitignored, empty or comment-only, CRLF, a hostile
workspace (a content filter bound to the ignore file and the config), a symlink, a
non-repository, and a repository without commits; plus 14 more with different
`user.signingkey` values (unset, empty, a literal key, `sk-`, `ecdsa-`, `key::`, an
existing and a missing file, `~` paths, a GPG key id, a directory, look-alike
prefixes, leading space). 1,056 cases cross them with four exception-source
configurations (committed blob versus working copy, attestation-at-HEAD required),
three unvetted-acceptance values, and four honor-flag values, and with twelve
`vetting_signing_key` and trust-format settings.

**Results**
- **0 divergences** on 1,056 cases (bash 5.2.21, `LC_ALL=C.UTF-8`); no marker file
  from the hostile workspace in any case.
- **Mutation testing.** 19 planted bugs, run in parallel copies of the module. All
  behavioural ones were caught after widening the honor-flag values; the survivors
  are equivalent (a tag-empty guard a vetted line never needs, a default for a
  missing distance a vetted line never lacks, the exception-source test that only
  ever returns `true` or `false`, and a file check before a read that fails anyway).

**Findings about the v2 bash**
1. **The signing-key check is a prefix test.** `_vetting_ssh_key_usable` accepts any
   value beginning `ssh-`, `sk-ssh-`, `ecdsa-sha2-`, or `key::`, so a key id such as
   `ssh-foo` counts as usable. It is a UX heuristic (the signature is verified
   against the trust root afterwards), not a security decision.
2. **A tag's committed exception list is read with `git show <tag>:<file>`**, which
   applies no content filters. The hostile-workspace fixture, which binds a clean
   filter to the ignore file, ran nothing.
3. **An ignore file that is a directory yields entries.** `git show rev:dir` prints
   the tree listing, which the reader then strips and returns as fingerprints (for
   example `tree HEAD:.betterleaksignore`). They match no finding, so it is
   harmless, but it is not "empty".

**Not done:** `TestExceptionsLiveOracle` is written but not run (no Go on the VM).
`vetting_attest_repo`, `_vetting_inline_attest`, `_vetting_acknowledge_exceptions`,
and `vetting_signing_setup_assist` are still bash (pilot 9). The mutation survivors
above were examined, not removed.

## Pilot 9: attestation: `vetting_attest_repo` and friends (2026-11-18)

**What was built** (`go/internal/vetting/attest.go`, about 385 lines):
`vetting_attest_repo`, `_vetting_acknowledge_exceptions`, `_vetting_inline_attest`,
`vetting_signing_setup_assist`, and `upsert_yaml_scalar_in_file`. This completes the
port of `lib/vetting.sh`.

**Method.** Real SSH signing: `setup.sh` generates throwaway ed25519 and RSA keys
and 11 template repositories (clean with a signing key, no key, a GPG key id, an
untrusted key, dirty, already attested, with recorded exceptions, with legacy
exceptions, a hostile workspace whose config names a program for every signing and
key-lookup hook, one that sets only `gpg.ssh.defaultKeyCommand`, and a non-repo).
Each case copies what it needs into a fresh run directory and runs one function:
`attest` against 7 user configurations, flags and messages; `ack` with a stub
scanner producing accepted, mixed, unlisted, and no findings, with and without
`betterleaks`; `inline` with prompt sequences; and `assist` against homes with
different SSH keys (none, ed25519 and RSA, RSA only, an empty key file, a blank first
line). Prompts run on a pseudo-terminal. Compared per case: output streams, the
audit/warn log, the exit status, the tags and the headers of their objects (the
signature body is removed; the tagger date is pinned), markers from the hostile
workspace's programs, the global git config, the user config and its mode.
Diagnostics from `git`, `ssh-keygen`, and `gpg` are filtered from the stream; their
wording differs between versions. Printed public keys are masked. 997 cases.

**Results**
- **0 divergences** on 997 cases (bash 5.2.21, git 2.56, `LC_ALL=C.UTF-8`): 128
  signed tags created, 26 "already attested", 39 inline attests that verified, 22
  that were removed because they did not verify, and 14 signing setups performed.
  **No marker file in any case**: none of the hostile workspace's programs ran while
  signing.
- **Mutation testing.** 29 planted bugs, run in parallel module copies. Four
  survived at first and led to new fixtures (the `defaultKeyCommand` pin, the
  non-"accepted" findings, odd `--yes` values, an empty key file); all are now caught.
  Two survivors remain: a check for `jq` that needs a PATH without it, and a
  `chmod` that the Go write makes redundant.

**Findings about the v2 bash**
1. **On git 2.43.0 (Ubuntu 24.04's package), `git tag -s` with a failing SSH signer
   exits 0 and creates an UNSIGNED tag.** Reproduced directly: with
   `user.signingkey=ABCD1234` git prints "Couldn't load public key" and exits 0, and
   the tag exists with no signature. git 2.56 fails correctly ("unable to sign the
   tag"). On 2.43, `vetting_attest_repo` therefore prints "created signed attestation
   tag" for an unsigned one. The launch gate still refuses it (an unsigned tag does
   not verify), and the inline attest re-verifies and deletes it, but `sandbox vet`
   reports success, and the stray tag makes the next `sandbox vet` say "already
   attested" while the gate keeps saying "unvetted". The appliance image's git
   version decides whether this bites; the Go port should check that the tag verifies
   after creating it (as the inline path already does) rather than trust git's exit
   status. The port currently reproduces the bash, so it inherits this on 2.43.
2. **"Already attested" only means a tag of that name exists.** It does not check
   that it verifies. By design (the code comments say a tag we did not create is not
   ours to touch), but it compounds finding 1.
3. **Every program-selecting hook is pinned for signing**, and the corpus confirms
   it: signer, OpenPGP, X.509 programs, and `defaultKeyCommand`. A repo that sets
   only `defaultKeyCommand` (git runs it to find a key when none is configured) ran
   nothing.
4. **The signing setup writes the operator's global git config** after a y/N prompt
   (`gpg.format`, `user.signingkey`); with a GPG commit-signing identity it offers
   the attestation-only key instead and leaves git alone.

**Not done:** `TestAttestLiveOracle` is written but not run (no Go on the VM). GPG
signing and a PATH without `jq` are not covered. The VM's git was upgraded from 2.43
to 2.56 (git-core PPA) so the oracle matches the host; the goldens of pilots 1 to 8
were generated under 2.43 and still match the port, so none of them depends on it.

## Summary after nine pilots (2026-11-18)

**Where it stands.** The secret gate (`finding_is_encrypted`, `is_path_masked`,
`_leakscan_finding_accepted`, `scan_repo_secrets` and its config and scanner helpers,
`secret_gate_repos`) and all of `lib/vetting.sh` are ported and merged to `v3`: about
2,400 lines of bash (1,423 of them `vetting.sh`; roughly 1,000 from `filesystem.sh`,
`config.sh`, and `profile.sh`). Production Go is about 4,500 lines (1.9 Go lines per
bash line, much of the bash being comments), tests 1,500 lines, plus generators, oracle
scripts, and fixtures. Every unit has 0 divergences from the bash on its corpus
(about 85,000 cases in total), a mutation-tested corpus, and a live-oracle test.
That is about a quarter of the roughly 10,000 candidate lines estimated earlier in
this document; the other three quarters are not started.

**What the method found.** Porting under differential testing surfaced about thirty
behaviours of the v2 bash that its tests and comments do not state. Most are
harmless or fail safe; they are listed per pilot above. The ones worth a decision:

| Finding | Pilot | Why it matters |
|---|---|---|
| A zero-padded `08` or `09` in `vetting_max_commits_behind` / `vetting_max_age_days` defeats "most restrictive cap wins" (an arithmetic error makes the comparison false) | 5 | An overlay's tighter cap can be ignored; depends on who can edit the user config |
| git 2.43 creates an unsigned tag when its SSH signer fails, and `sandbox vet` reports success | 9 | Misleading success and a stray tag that blocks re-attesting; the gate still refuses it |
| The gate de-inflates betterleaks' `StartColumn` by one, but 1.10.0 reports exact columns (my first note of an end-column error was wrong; see pilot 1, finding 3) | 1 | Containment is one column too strict at the start; no practical effect |
| The gate's `[[ -z file ]]` check and its sibling in `secret_gate_repos` cannot fire (`read` collapses empty fields) | 3, 4 | A finding with an empty `File` is classified from shifted fields |
| Non-ASCII directory names are never excluded from the scan (git quotes them) | 3 | Fails safe; costs scan time |
| `masked_paths:` is literal (no globs) and cannot list `-n`, `-e`, `-E` | 2 | Documentation gap; a surprise for a user who writes `*.pem` |
| An unknown posture enforces unless there is no trust root | 7 | Unreachable today (callers normalize) |

None is a critical vulnerability. Two are worth fixing in Go before release (the
arithmetic cap comparison and the unsigned-tag check); the rest are documentation or
dead-code clean-ups. The port deliberately reproduces all of them, so that "port" and
"fix" are separate, reviewable changes.

**What the differential method costs.** The first unit took a working session because
the harness had to be built. Later units cost mainly the port and the fixtures, but
each new kind of dependency added work once: a stub scanner (pilot 3), a pseudo-terminal
runner (4), a fixed clock (5), git repositories with signed tags and a hostile workspace
(6), real SSH signing (9). The oracle needs a Linux machine with the repo's `lib/`, a
newer git than Ubuntu 24.04 ships (see pilot 9), and Python for the terminal cases.
The corpora are large: 3,058 files under `go/` (about 8.7 MB raw, 4.5 MiB packed; an earlier
"20 MB" figure was `du` rounding every small file up to a 4 KB block). The file count, not the
bytes, is what makes the pull request heavy to review; trimming it is under way (see the handoff
below).

**What it does not show.** The stubs replace betterleaks, so nothing here tests what
the scanner finds. The mocks for audit, vetting, and the terminal stand in for modules
not yet ported, so cross-module contracts are untested until those exist. The oracle is
the bash's behaviour on one Linux image and one macOS host, not a specification; where
the two differ the port follows the oracle. The live-oracle tests were first run after the summary (see "Live oracle and CI" below).

**What is left, and a revised estimate.** About 7,600 of the roughly 10,000 candidate
bash lines remain: `checks`, `link`, `audit`, `onboard`, `agents`, `catalogue`,
`profile`, `credentials`, `tier`, `certs`, the rest of `config` and `filesystem`, and
about half of `bin/sandbox`. These are not like the units done so far. Those were pure
text and git; most of what remains calls `docker`, `limactl`, `kubectl`, `jq`, and the
network, so a differential harness needs mocks of those tools, and `bin/sandbox` is a
command-line surface where output and exit codes are the contract. My expectation,
which is a judgement and not a measurement, is that these units cost several times
more per line than the ones done, and that the CLI and `audit` (which writes the
session record) are the hardest. I would not extrapolate a total from the nine
pilots: the data say the method works and is affordable for self-contained logic, and
say little about the orchestration code.

**Recommendation.** Keep the bash as the oracle and continue unit by unit, in this
order: `config`, `profile`, `checks`, `tier`, `catalogue`, `audit` (policy and record
format), `link`, `onboard`, `agents`, `credentials`, then the CLI last. Before that,
decide (a) which findings above to fix in Go for v3.0.0, (b) whether the live oracle
runs in CI (it needs a Linux runner with Go, git 2.56 or newer, `ssh-keygen`, `jq`, and
Python), and (c) how to trim the test data. Move the shared helpers (YAML and overlay
reading, `readTab`) out of `internal/gate` into a common package at the same time, so
the import-graph check in section 5.1.1 has the layout it expects.

**Decided since (2026-11-18).** (a) Fix every quirk found, each as a named deviation (see
"Fixes" below). (b) Yes: `.github/workflows/go.yaml`. (c) Trim by file count, re-checked by
planted bugs (handoff item 2). The shared helpers moved in `77e6c48`.

   the operator, world-writable, or group-writable by a group other than root's or, on macOS,

The in-VM CLI still uses v2's paths and wording (`/root/.sandbox/logs`, "Active pods in namespace

**Sync gate rule layer (2026-11-25).** `go/internal/host/syncgate` and `go/internal/host/gitobj`
implement 5.6.2's rules as host-side functions; no engine feeds them yet.
- Paths (rules 1-3, 6; 5.6.4 item 1): `Classify` validates and classifies a VM-origin path (apply,
  keep local, quarantine, or the ref, HEAD, index, object, attributes rules). Protected names are
  compared with a key that may over-match but never under-match the host file system: full and
  simple case folding, a coarse normalization (non-ASCII and base-plus-mark dropped), NTFS
  trailing dots, short names, and streams. `TestKeyCoversHostAliases` asks the real file system
  which spellings alias; on APFS it found that sharp s is `ss` and the fi ligature `fi` (full case
  folding), which simple folding had missed (`.lfscon` + U+FB01 + `g` was `.lfsconfig`). Any
  `.git` deeper in the tree (a nested repository) and any unrecognised `.git` path quarantine.
- Rule 8: `CheckAttributes` (driver attributes and `[attr]` macros; the exact LFS triple passes).
- Rule 7: `ParseIndex`/`WriteIndex` (versions 2-4, SHA-1 and SHA-256, strict; tested against git
  and fuzzed) and `MergeIndex` (three-way by path; VM entries withheld for protected paths,
  gitlinks, type changes, objects the host lacks). The writer keeps intent-to-add, which rule 7 does
  not list as a hiding flag (clearing it would stage an empty file).
- Rule 6: `gitobj` (loose objects, packs with deltas, `VerifyLoose`, `VerifyPack`, `IsAncestor`;
  tested against git) and `DecideRefs`/`DecideHead`/`ParsePackedRefs` (fast-forward of unprotected
  branches only; protected, rewinds, deletions, both-sides moves, alias spellings quarantined).
- The applier: `os.Root`-confined, refuses a write through a parent symlink, conflicts by
  last-synced fingerprint, type changes, escaping or protected symlink targets, size limits;
  atomic rename; an interrupted batch resumes.
- Testing note: `internal/archtest` shells out to `go list`, so Go's test cache cannot see what it
  depends on; run it with `-count=1` (a cached pass hid a missing rule for one commit).

**netd spike: blocked on the owner (2026-11-25).** Lima cannot give the VM a host-controlled
network as its only NIC: a `socket:` network adds a second interface, and Lima's built-in

stack as the only NIC, the stack being gvisor-tap-vsock (gvproxy) with a per-destination filter
added. The spike needs vfkit v0.6.4 (an entitlement-signed binary from crc-org/vfkit) and
gvisor-tap-vsock v0.9.0, downloaded and run; the session's permission policy refused downloading
and running third-party binaries unattended, so it waits for the owner. Two owner decisions come
with it: allowing those downloads for the spike, and whether the module may take its first
third-party dependency (gvisor-tap-vsock, which brings gVisor's netstack) for netd, or whether
netd runs gvproxy as a separate pinned binary with a filter in front.

**Image build tool comparison (item 8, for the owner, 2026-11-25).** Requirements from 5.3 and
5.2.5: pinned inputs, reproducible filesystem content, signed artifacts with provenance, a
read-only dm-verity system disk plus a separate state disk, EFI boot on vz and qemu, amd64 and
arm64, and a CI build.

| | mkosi (current) | Packer | Scripted mmdebstrap + systemd tools |
|---|---|---|---|
| How it builds | Installs packages into a directory tree, then assembles partitions, UKI, and verity offline | Boots a VM from an installer or cloud image and runs provisioning scripts inside it | mmdebstrap builds the root tree; our script runs systemd-repart, veritysetup, ukify, bootctl |
| Reproducible content | Designed for it (SOURCE_DATE_EPOCH, fixed seeds); here: identical root and kernel, initrd metadata differs on v24 | Poor: the image is a booted machine's disk (logs, random seeds, journal, cloud-init state), which must be scrubbed by hand | Good: mmdebstrap is built for reproducible trees; the rest is ours to get right |
| dm-verity, UKI, partitions | Built in (Verity=, UKI, repart definitions) | Not provided; post-processing scripts | Same tools mkosi wraps, wired by us |
| Root on the builder | Root, or unprivileged user namespaces (blocked by Ubuntu's default AppArmor) | No root; needs KVM (or vz) on the builder | mmdebstrap's fakechroot mode needs no root; repart and veritysetup work on image files offline |
| Both architectures | Native build per architecture (or emulated) | Per-architecture VM; arm64 on an arm64 runner | Per architecture; foreign arch via qemu-user is possible but slow |
| Code we own | A config file and a post-install script | Templates and scripts | The most: the assembly mkosi does for us |
| Pinning the lockfile (decision 6) | Feed a local package repository | Feed a local repository inside the build VM | mmdebstrap takes a local repository directly |

Recommendation: **keep mkosi**, pinned to a newer upstream release (which item 7 needs anyway),
with builds as root on CI runners and the build VM; root on a dedicated image builder is the norm
and touches no workstation. It is the only option that provides verity, UKI, and partition
assembly without our own code. Packer's booted-machine model works against reproducibility, which
5.3.2 makes a MUST. A scripted mmdebstrap build is the fallback if mkosi's root requirement or its
reproducibility proves unworkable: rootless and fully ours, at the cost of reimplementing mkosi's
assembly.
