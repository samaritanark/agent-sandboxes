# S2 — Per-agent brokering and harness updates

**Status:** started. Only the harness-update questions (§5.7.1, Appendix D)
were investigated. The OAuth and credential-brokering questions (token
endpoints, placeholder-only operation, refresh behaviour, account identity,
runtime-written files, exec-plugin classification) were not touched, so none of
the exit criteria are met.

## Environment

- Installers downloaded 2026-11-18 from each vendor's documented URL, read (not
  executed) on the Mac, then run as an unprivileged user inside the throw-away
  Lima VM (Ubuntu 24.04, arm64, full outbound access) with a `curl` wrapper that
  logged every URL requested. Redirect targets were found with a separate
  `curl -sIL`.
- On the Mac, Claude Code 2.1.327 and Codex 0.170.0 are installed (macOS
  builds). Copilot, Grok, and opencode are not. Nothing was run on the Mac
  except `--version` and `--help` with auto-update switches set; no harness was
  logged in or started a session.
- Versions installed in the VM: Claude 2.1.327 (pinned), Codex 0.170.0 (pinned),
  Copilot 1.0.114 (latest), Grok 1.0.89 (latest stable), opencode 1.0.180
  (pinned; this is the OpenCode 1 line, and the installer says OpenCode 2 has a
  separate installer).

## Findings that change the design

1. **The updater must verify, not trust the vendor script.** Only Claude
   publishes something verifiable beyond a same-origin digest, and its own
   installer does not verify it; Copilot's script skips its check when the
   digest file is missing; Grok's and opencode's scripts verify nothing. §5.7.1
   now says the updater verifies itself and adds a **checksum** level between
   signed and TLS-only.
2. **Egress for the updater microVM differs by vendor and includes redirect
   hosts.** GitHub-hosted releases redirect to `release-assets.githubusercontent.com`,
   so an allowlist of `github.com` alone would fail. Codex needs a GitHub
   fallback list. Hosts above are what these runs used and may change.
3. **Copilot downloads updates into a package cache and applies them at the next
   launch** (per its own help text), and with auto-update disabled it ignores
   any newer version already in that cache. The harness's cache directory must
   not persist between sessions, and the disable switch must be set, or a
   replaced binary could run. Claude and Codex keep versions under their home
   directories and flip a symlink, which the §5.7 re-staged-home rule already
   discards at teardown; this was not tested.
4. **Not every vendor installs into a versioned directory.** Copilot and opencode
   write one binary in place, so the updater needs a per-version prefix for them
   (`PREFIX` works for Copilot; opencode's install directory was not made
   configurable in this run).
5. **Codex's `codex update` cannot pin**; use the installer with
   `CODEX_RELEASE`.
6. **Binaries need a Linux libc or not.** Codex and Grok are static; Claude,
   Copilot, and opencode are dynamic (glibc in the Ubuntu guest image worked; an
   Alpine/musl guest image was not tested).
7. **A correction to my own earlier reading.** The VM has no `strings` command,
   so the first searches for update-related names returned nothing and I wrongly
   read that as "none". A raw `grep -a` of each binary found the names in the
   table.

## Claude Code with a placeholder (2026-11-26, S8)

Claude Code 2.1 (built by `sandbox rebuild`) in a Kata session, `CLAUDE_CODE_OAUTH_TOKEN` holding
a broker placeholder, the broker injecting a fake `sk-ant-oat01-` token toward
`api.anthropic.com` (S8, "Claude Code through the broker"). It accepts the placeholder without
checking its shape and sends it as a bearer token on its authenticated calls: `POST /v1/messages`,
`GET /api/claude_cli/bootstrap`, `GET /api/claude_code/settings`, `GET
/api/claude_code/policy_limits`, `POST /api/eval/<sdk key>`. It also calls `HEAD /api/hello`,
`POST /api/event_logging/v2/batch`, and `GET /api/directory/server-urls` without any credential.
No other host was contacted in `-p` mode with a rejected token. With `CLAUDE_CONFIG_DIR` set it
keeps `.claude.json` in that directory and warns when it is missing. Not yet observed: a session
with a valid token (other hosts it may contact once signed in), and the `claude login` token and
refresh endpoints.

## Codex with a placeholder (2026-11-26, S8)

Codex 0.172 (`sandbox rebuild`), a ChatGPT login whose `auth.json` the launch writes: an
`alg: none` JWT access token with the real expiry and account claims and the broker placeholder
as its signature, an id token with the account's claims, a dummy refresh token. Codex accepts it
(`codex login status`: "Logged in using ChatGPT"), checks no signature, and sends the access token
only to `chatgpt.com`: `GET /backend-api/codex/models`, `/backend-api/wham/accounts/check`,
`/backend-api/wham/settings/user`, `/backend-api/ps/plugins/installed`,
`/backend-api/ps/plugins/suggested/codex`, `/backend-api/ps/plugins/tooling-state/<name>`,
`POST /backend-api/ps/mcp`, `/backend-api/codex/analytics-events/events`; the model call goes
over a WebSocket first and falls back to HTTPS. Its source (`codex-rs/login`) refreshes at
`https://auth.openai.com/oauth/token` (JSON, client id `app_EMoamEEZ73f0CkXaXp7hrann`) five
minutes before the access token's expiry, eight days after `last_refresh`, or on a 401. Current
Codex also takes a workspace personal access token (`at-...`, `CODEX_ACCESS_TOKEN`), created in a
ChatGPT Business or Enterprise admin console; not used here (the owner has a personal login).
