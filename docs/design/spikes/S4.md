# S4 — Workspace sync

**Status:** started. The git-behaviour assumptions behind §5.6.2 rules 6 to 8
were checked, and a throw-away Go prototype read and rewrote real indexes. The
sync engine, the host-side gate, the entry-level index merge, path aliasing,
performance on APFS/ext4/NTFS, and the adversarial cases listed in §8 have not
been built or run, so none of the exit criteria are met.

## Environment

macOS 27.3 on an Apple M6, git 2.56.0 (Homebrew), scratch repositories in a
temporary directory, with `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, and
`GIT_CONFIG_NOSYSTEM` pointed at throw-away files so the operator's own git
configuration was never read. The reviewer (F1, F10) tested with git 2.43.0 on
Linux; **git 2.43.0 itself was not tested here**.

## Index parser feasibility (Go prototype, rule 7)

A scratch Go program (outside the repository, `go-git/v5` v5.19.3, Go 1.27.3)
decoded and rewrote git index files built with git 2.56.0. Inputs: a
100,000-entry index in versions 2 (with the TREE extension), 3 (1,000
`skip-worktree` and 500 `assume-unchanged` entries), and 4; and a merge-conflict
index with stages 1 to 3.

| Check | Result |
|---|---|
| Decode versions 2, 3, 4 at 100,000 entries | 36 to 57 ms each; versions, entry counts, `skip-worktree` (1,000), conflict stages, and the cache-tree extension all reported correctly |
| Rewrite as the gate would: clear `skip-worktree`, drop extensions, zero stat data, sort, write version 2 | 32 ms; output 9.4 MiB |
| Does git accept the rewritten index? | **Yes.** `git ls-files --stage` was identical to the original for all 100,000 entries, from both the v3 and v4 inputs |
| Were the hiding flags removed? | **Yes.** The original had 500 `h` (assume-unchanged) and 1,000 `S` (skip-worktree) entries; the output had 100,000 `H`. The library does not model `assume-valid` at all, so it is dropped on decode |
| Hostile inputs (empty, garbage, truncated, bad version, bad checksum, header claiming 67 million entries with none present) | All rejected with an error (`EOF`, `malformed index signature`, `unsupported version`, `invalid checksum`); no panic; no allocation growth (0 MiB; peak RSS about 5 MiB) |
| Fuzzing the decoder (Go's built-in fuzzer, seeds: v2, v2 with TREE, v3, v4, conflict, and a bare header) | About 2.7 million inputs over two 60-second runs: no panic, no hang, no allocation above a 64 MiB guard |

Limits of this result:
- It exercises the **library's** decoder, not the strict parser the design
  calls for. The library does not validate entry paths (names containing `..`,
  `.git` components, absolute paths, case or Unicode aliases), size or entry
  limits, or gitlink and file-type changes, so the gate still has to enforce all
  of that itself; I did not test what the library does with such names.
- The entry-level three-way merge, the lock protocol (`.git/index.lock`), and
  the HEAD-derived reconcile fallback were not built.
- Stat data was zeroed, not re-derived; the cost of git re-statting every file
  on first use is the same re-check measured in S1.
- Two minutes of fuzzing is a smoke test, not assurance.

## Path aliasing on APFS (the Mac's default volume, rule 2 and N-11)

Method: in a scratch directory on this Mac's data volume, create
`repo/.git/hooks/pre-commit`, then try other spellings of the same path. I did
not capture `diskutil` output, so the volume's case sensitivity is shown by
behaviour only.

| Spelling | Result |
|---|---|
| `.GIT`, `.Git`, `.gIT` | **Resolve to the real `.git` directory.** A write through `.GIT/hooks/pre-commit` replaced the real hook's contents |
| `.//.git` | Resolves to the real directory (path normalisation, not aliasing) |
| `.git.` (trailing dot), `.git ` (trailing space), `.g<U+200C>it` (zero-width non-joiner), fullwidth `ｇ` | Separate paths on APFS; no alias |
| NFC `café` vs NFD `café` for a directory | Resolve to the same directory (normalisation-insensitive) |
| `file` and `File` | One file; the second write replaced the first |

This confirms why §5.6.2 requires case-insensitive and
Unicode-normalisation-insensitive classification on APFS. Not tested: NTFS (where
trailing dots and spaces, short names such as `GIT~1`, and alternate data
streams alias `.git`) and HFS+ ignorable characters, so the classifier's rules
for those hosts are still unverified.
