# S1 — Kata without Kubernetes: storage, networking, sizing

**Status:** partial. Kata with Cloud Hypervisor runs under containerd with no
Kubernetes; the mount set, shared-tree coherence, the per-session network
topology (namespaces, link, nftables, CNI `ptp`), and first footprint numbers
were measured on one machine, as were Codex's bubblewrap and a 100,000-file
repository. Exit criteria are not met: large-repository performance is poor
under either cache mode, Kata's shipped configuration does not apply guest
seccomp, and the stalls are unexplained.

## Packaging findings

- The `kata-static` 4.4.0 bundle contains only the **Rust** shim
  (`/opt/kata/runtime-rs/bin/containerd-shim-kata-v2`), and its shipped configs
  cover QEMU, Dragonball, Firecracker, and OpenVMM, with **no Cloud Hypervisor
  config**. The Cloud Hypervisor config (`configuration-clh.toml`) and the Go
  shim are in the separate `kata-go-static` bundle. Image build must pin both,
  or move to a Rust-runtime Cloud Hypervisor configuration if one exists.
- Kata 4.4 rejects a custom `KATA_CONF_FILE`: `invalid KATA_CONF_FILE ... only
  shipped Kata configuration files are accepted`. Naming the shim
  `containerd-shim-kata-clh-v2` did not select Cloud Hypervisor (it used the
  default `configuration-qemu.toml`). What worked:
  `ctr run --runtime io.containerd.kata.v2 --runtime-config-path
  /opt/kata/share/defaults/kata-containers/configuration-clh.toml`.
  `sandboxd` will have to pass the runtime config path through containerd
  runtime options; editing the shipped file in place is accepted by the shim
  but is not a design.
- The shipped `enable_annotations` list is only `enable_iommu`, `kernel_params`,
  `kernel_verity_params`, so per-session CPU and memory cannot be set by
  annotation. Defaults: 1 vCPU, 2048 MiB. How `sandboxd` sizes microVMs (OCI
  resource limits, or a config per size class) is open.

## Results

**Canary (§5.2.3 check 3, partial).** A Kata microVM with Cloud Hypervisor
booted, ran a command, and tore down cleanly. `uname -r` inside reported
6.18.62, the appliance VM reports 6.8.0-147, so the guest has its own kernel.
Start (image cached) 6.8 s and 7.2 s wall time, nested on M6. The canary did
not test reaching a gateway.

**Mount set.** One microVM with `/workspace` read-write, a file mask, a
directory mask, and a read-only overlay:

| Mount | Result |
|---|---|
| Workspace read-write | Reads and writes work; two microVMs on one tree see each other's new files on first look |
| Read-only directory overlay | Guest write fails with `Read-only file system`; underlying files intact |
| Empty directory mask over `.kube/` | Guest sees an empty directory; underlying `config` intact |
| Empty file mask over `.env` | Guest reads it as empty and writes land in the mask file, **but the real file underneath was truncated to 0 bytes at microVM start**, before any guest access (reproduced in isolation) |

The file-mask truncation is Kata's mount-point creation, not guest behaviour.
It does not weaken the design (masked paths are never in the VM copy, §5.6.2
rule 1) but P-12 cannot rely on a file mask to *protect* a file that is
present, and the sync gate must not report the placeholder as a change. The
fallback in this document's S1 section (sync exclusion plus directory
overlays) already covers it.

**Concurrent appends.** Two microVMs each appended 300 lines to one file:
600 of 600 lines present.

**Cache coherence between microVMs.** With the shipped `virtio_fs_cache =
"auto"`, microVM P overwrote a 3-byte file with 8 bytes and microVM S, reading
immediately, got the first 3 bytes of the new content (`val`): a **stale file
size** within the 1 s attribute cache. Later iterations with unchanged size
read correctly. With `"never"` the same test read the full value every time.
`"metadata"` and `"always"` cache attributes without expiry, so I did not test
them for coherence and do not expect them to be safe for a shared tree.

**Metadata performance, 20,000 small files (cold unless noted):**

| Mode | find | stat all | read all | create 2k | Notes |
|---|---|---|---|---|---|
| `auto` (shipped) | 0.66 s | 0.66 s | 7.6 s | 1.2 s | stale-size window up to 1 s |
| `never` | 12.3 s | 24.7 s | 17.8 s | not rerun | coherent; about 19× slower on metadata |
| `metadata` | 0.70 s | 0.54 s | 6.4 s | not run | attributes never expire |

The 20,000-file microbenchmark overstates the cost of `git status`; see the
100,000-file measurement below.

**Footprint (one idle microVM, host-side RSS).** About 197 MiB: Cloud
Hypervisor 160 MiB, the Kata shim 32 MiB, two virtiofsd processes 7 MiB. Guest
memory was 2 GiB configured, 1.9 GiB visible. Teardown of two microVMs took
1.1 s with no leftover processes.

## Networking: per-session namespace, link, nftables (P-03, P-09 prototype)

Topology built by hand in the appliance VM, two sessions (A, B):
`microVM --veth-- [gateway namespace gwX] --veth uplink-- [root ns] --NAT-- eth0`.
Guest link `10.200.X.0/30`, uplink `10.201.X.0/30`, each gateway namespace with
`ip_forward=0`, IPv6 disabled, and an nftables `inet` table (input policy drop;
accept only from the guest link: TCP 443, UDP/TCP 53; drop-and-log everything
else; drop traffic whose source is not the guest's address or whose
destination is not the gateway's link address; forward policy drop). A toy
gateway answered on the link address (TCP 443, TCP 8080, UDP 53). Guest A ran
with `CAP_NET_ADMIN` to model a hostile root; guest B had default capabilities
(`ip addr add` was denied). Each microVM was started with
`ctr run --with-ns network:/var/run/netns/<agent-ns>`.

| Attempt from the guest | Result |
|---|---|
| Gateway TCP 443; UDP 53 | Answered (`gateway-A:443`, `dns-A`) |
| Gateway undeclared TCP 8080; ICMP to the gateway | Blocked, logged (`sbx-drop`) |
| Gateway's uplink address `10.201.1.2:443` (weak-host case) | Blocked, logged (`sbx-weakhost`) |
| Root-namespace uplink `10.201.1.1`; internet by IP `1.1.1.1:443` | Blocked |
| Session B's gateway and uplink addresses (cross-session, P-09) | Blocked, both directions |
| Source spoofing (own extra address; an address from session B's range) | Blocked, 6 packets logged (`sbx-spoof`) |
| On-link route to `1.1.1.1`; static ARP entries mapping `10.201.1.2`, `10.201.1.1`, `1.1.1.1`, `10.200.2.1` to the gateway's MAC | Blocked; the weak-host rule fired for the uplink address. Static entries were set with BusyBox `arp -s`, which printed no error, but I did not re-read the neighbour table to confirm each took effect |
| Declared gateway after all of the above | Still answered |

Findings:
- **The topology works with Kata.** The guest gets the interface and address
  from the namespace, the link is the only path, and nothing beyond the
  gateway's TCP 443 and DNS ports answered.
- **The weak-host defence is needed.** The gateway namespace answers ARP for its
  uplink address on the guest link and would accept a connection to a listener
  bound to all addresses. The `daddr != link address` rule is what stopped it
  (3 packets).
- **Forwarding is blocked before nftables.** With `ip_forward=0`, packets for
  other addresses never reach the nft forward chain (counter stayed 0), so the
  sysctl and the chain are two independent layers.
- **Namespaces are single-use.** After a microVM is killed, Kata leaves its
  traffic-control redirect on the guest-side interface. A new microVM on the
  same namespace failed: `Failed to add qdisc for network index 2 : file
  exists`. `sandboxd` must delete and recreate both namespaces per session.
- **The guest keeps the interface name it is given** (`agA0` in the manual
  topology, `eth0` under CNI).
- **No resolver in a new namespace.** The gateway namespace inherited
  `nameserver 127.0.0.53`, which does not exist inside it, so name resolution
  failed while NAT by IP worked (HTTP 301 from `1.1.1.1`). The gateway's
  upstream resolver address must be set explicitly (§5.8.9).
- **CNI works.** The `ptp` plugin run inside the gateway namespace with the
  agent namespace as `CNI_NETNS` (`ip netns exec gw env CNI_COMMAND=ADD ...
  ptp`) placed the host end in the gateway namespace and the guest end in the
  agent namespace, with no veth end left in the root namespace. A microVM on it
  got `eth0 10.202.1.2/30`, reached the gateway at `10.202.1.1:443`, and could
  not reach `1.1.1.1`. `ptp` installs no default route, so "no route except the
  gateway" holds by construction on the guest side (a hostile guest can still
  add routes; the gateway namespace does not forward). `DEL` returned 0 and left
  no address reservations. Not tested: the `bridge` and `firewall` plugins, and
  driving this through go-cni from a Go program.
- **Not tested:** IPv6 on the link (the guest kernel has its own link-local
  address; the gateway namespace had IPv6 disabled and the nft table is `inet`),
  a real gateway (Envoy), more than two concurrent sessions, dependency links,
  and start-up time with namespaces provisioned ahead of the microVM.

## Large repository: 100,000 files

Repository: 100,000 small tracked files in 1,000 directories, 809 MiB on disk,
one commit, generated in the appliance VM (ext4). `git status` run inside one
Kata microVM (root, `ubuntu:24.04` image with git, workspace via virtio-fs).
The first guest run has to re-check every file because stat data differs from
what the index recorded.

| Operation | Native (appliance VM) | microVM, `auto` | microVM, `never` |
|---|---|---|---|
| `git status`, first run | 0.11 s (cold cache) | 11.0 s | 23.3 s |
| `git status`, repeat | 0.07 s | 12.9 s, 10.1 s | 23.0 s, 22.9 s |
| `find` over 100,000 files | not run | 4.0 s | 1.4 s |
| `git ls-files` | not run | 0.6 s | 0.5 s |
| edit one file, then `git status` and `git diff --stat` | not run | 16.3 s | 44.1 s |

Findings:
- **Both modes are slow for a repository this size.** Repeat runs are no faster
  than the first, because every `git status` re-`lstat`s 100,000 files across
  virtio-fs (with `auto` the attribute cache expires after 1 s).
- **`never` is about 2× slower than `auto` for `git status`**, not the 19× the
  20,000-file microbenchmark suggested, which supports the OQ-15 choice of
  `auto`. The `find` numbers run the other way (`never` was faster on that
  run); I did not investigate, and a single run is not a trend.
- **This is a real usability risk.** Coding agents run `git status` often, and
  10 to 13 s per call on a 100,000-file repository is a visible cost against
  v2 on Linux. It is the shared-tree design (the working tree on the host side
  of virtio-fs), not the cache mode, that causes it.
- **Not tried at first measurement** (git settings, a virtiofsd thread pool,
  and vCPU counts were tried afterwards, below): a guest-side
  file-system monitor (it would see only changes made inside the guest, not the
  sync tool's writes); a workspace on a guest block device with the sync tool
  moving changes through the guest agent (a larger design change); smaller
  repositories (measured below).

## `git status` latency by repository size, and tuning attempts

Synthetic repositories of uniform small files (about 10 lines each), 100 files
per directory, one commit; `git status --short` inside one Kata microVM
(`auto`, default virtiofsd arguments, 1 default vCPU), three runs 3 s apart
(runs back to back are faster, because the 1 s attribute cache is still warm;
spaced runs are the realistic case). The first run also refreshes the index.

| Tracked files | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| 200 | 310 ms | 269 ms | 240 ms |
| 1,000 | 257 ms | 213 ms | 217 ms |
| 5,000 | 377 ms | 323 ms | 332 ms |
| 20,000 | 1,206 ms | 1,049 ms | 1,035 ms |
| 100,000 | 11,835 ms | 9,563 ms | 9,756 ms |

For scale, the largest of the owner's local repositories has 4,611 tracked
files and most have under 900, with at most a few hundred untracked files, which
puts them in the 0.2 to 0.4 s range here. Not measured: native `git status` for
small repositories, deep directory trees, large ignored trees, and v2's
timings for comparison.

Two features of the curve: a fixed cost near 100 ms per process (`git
--version` in the guest takes 93 to 130 ms; the container root file system is
also served over virtio-fs), and a knee between 20,000 and 100,000 files (5× the
files, about 10× the time).

**Where the 100,000-file time goes** (microVM, `auto`, runs 3 s apart):

| Operation | Time |
|---|---|
| `git status --short` (baseline) | 8.8 to 9.8 s |
| `git diff-files -q` (stat tracked files only) | 5.8 s |
| `git ls-files -o --exclude-standard` (directory scan only) | 4.6 to 4.7 s |
| `git status --short -uno` (skip the untracked scan) | 6.2 s |
| `status` with `core.untrackedCache=true` | 10.9 s the first time (builds the cache), then 6.5 to 6.7 s |
| `status` with `feature.manyFiles=true` (index v4 plus untracked cache) | 6.5 to 6.7 s |
| `status` with `core.preloadIndex=false` | 15.5 s |

**Other tuning attempts**
- `virtiofsd --thread-pool-size=16` (pool is off by default): no improvement;
  slightly slower at every size (100,000 files: 10.8 to 13.2 s).
- Guest vCPU count (`nerdctl --cpus 1, 2, 4`): inconclusive. Baseline medians
  were about 8.8 s, 6.1 s, and 9.0 s, and run-to-run noise was about 30%. I did
  not confirm how many vCPUs Kata actually gave the guest in each case, and the
  git-setting variants ran against an index already converted by earlier runs,
  so those three runs are not independent. Treat as no demonstrated effect.
- Not tried: a custom virtio-fs queue count or size (`virtio_fs_queue_size` is
  1024), a block-device root file system, or other snapshotters.

**Options considered** (none implemented):
1. Git settings in the guest image: `core.untrackedCache`, `feature.manyFiles`.
   Free, measured at about one third off. Interaction: `feature.manyFiles`
   writes index version 4, so the host binary's index parser must read versions
   2, 3, and 4; the untracked cache is an index extension that the sync gate
   strips whenever it replaces the VM's index (§5.6.2 rule 7), so the cache
   would rebuild after each such sync.
2. A guest-local workspace (block device inside the microVM, sync through the
   guest agent): native git speed, but sessions could no longer share one tree
   (per-session copies, as macOS v2 does today).
3. A read-only git proxy in the appliance VM, reached over vsock, running an
   allowlist of read-only commands natively (the 100,000-file `git status`
   takes 0.07 s there). Biggest gain for large repositories; it runs git on
   agent-written content from agent-supplied arguments, so it needs hardened
   config and a security review.
4. A file-system monitor: rejected. The sync tool writes outside the guest, so
   the monitor would report stale status.

## Codex bubblewrap and in-guest seccomp

Image: `sbx-test:1`, built inside the appliance VM with nerdctl and buildkit
(`ubuntu:24.04`, `bubblewrap`, `git`; built in about 15 s with cached layers,
which also confirms the `sandbox rebuild` path works without Docker on the
host). Started with `nerdctl run --runtime io.containerd.kata.v2 --net none`
and the Cloud Hypervisor config as Kata's default. The probe was a Codex-style
invocation: `bwrap --new-session --die-with-parent --ro-bind / / --bind
/workspace /workspace --dev /dev --proc /proc --unshare-user --unshare-pid
--unshare-net`.

| Posture (all in the Kata guest, kernel 6.18.62) | Result |
|---|---|
| Root, default capabilities, default masked and read-only `/proc` and `/sys` paths | `unshare -U -r` works; `bwrap` fails: `Can't mount proc on /newroot/proc: Operation not permitted` (and without a user namespace, `Creating new namespace failed`, since `CAP_SYS_ADMIN` is absent) |
| UID 1000, all capabilities dropped, `no_new_privs`, default masked paths | Same failure |
| UID 1000, no capabilities, `no_new_privs`, masked paths removed (`--security-opt systempaths=unconfined`) | **`bwrap` works**: pid 2 inside, workspace written, `/usr` read-only, only `lo` visible. Guest seccomp was not in force here (`Seccomp: 0`) |
| Same, with guest seccomp enforced (`disable_guest_seccomp = false`) | Profile applied (`Seccomp: 2`, one filter) and **blocks user namespaces**: `unshare: Operation not permitted`; `bwrap` fails |
| Same, `seccomp=unconfined` | `bwrap` works |

Findings:
- **Kata does not apply guest seccomp by default.** The shipped configuration
  has `disable_guest_seccomp = true` ("container seccomp profiles are ... not
  applied within the guest"). With it, `/proc/self/status` shows `Seccomp: 0`
  even though the runtime was given the default profile. §5.5.2's requirement of
  a default seccomp profile in the guest is unmet until the image sets it to
  `false`; the P-02 test must read `Seccomp: 2` from inside the guest.
- **Bubblewrap needs two in-guest relaxations**, together: remove the masked
  and read-only `/proc` and `/sys` paths, and use a seccomp profile that permits
  user-namespace creation (and what bwrap then needs). Neither reaches outside
  the microVM. Taking them weakens in-guest defense in depth; keeping v2's
  `danger-full-access` for Codex keeps the posture intact. Open (OQ-16).
- A custom seccomp profile that allows user namespaces was **not written or
  tested**; only the default profile and "unconfined" were tried. Whether the
  default seccomp profile is compatible with the other four agents was not
  tested either (S2).
- The Rust `ctr` client cannot combine `--config` with an image, and has no
  `--no-new-privs` or `ALL` capability flag; `nerdctl` was the usable client for
  these postures. `sandboxd` will drive containerd through its API, so this is
  a test-tooling note only.

## Stalls (unexplained)

1. A coherence loop stalled at iteration 19: an `exec` into microVM `mvP`
   waited 2,113 s, and microVM `mvQ`'s Cloud Hypervisor and virtiofsd processes
   disappeared at 09:10:04 (journal: `clh is not running`, `Dead agent`). No
   OOM or kernel message was found.
2. The first 20,000-file `find` after switching to `never` ran to my 300 s
   timeout, although the same operation finished in 12 s on a later run.

Neither reproduced in roughly 450 further `exec` calls and about 12 further
microVM starts (including the networking tests), so I cannot say
whether these are a Kata or virtiofsd defect, a nested-virtualization effect,
or a test artefact. Treat them as an open risk for `sandboxd`'s watchdog design
(§5.4.3): a hung microVM must be detected and torn down without operator help.

### Soak test (2026-11-18, 13:11)

A detached script on the same VM, with every operation under a timeout and
state capture on any stall, while other tests (the S5 gateway work) ran
concurrently:

| Phase | Operations | Result |
|---|---|---|
| A: 60 full lifecycles (start, 3 execs writing to a shared directory, remove) | 60 starts, 180 execs, 60 removals | all succeeded; start median 9.9 s (p95 11.1 s, max 11.6 s), exec median 239 ms (max 1.0 s), remove median 623 ms |
| B: two long-lived microVMs sharing one tree, 400 alternating write and read execs | 800 execs | all succeeded; write median 38 ms, read median 48 ms, max 296 ms |
| C: 15 minutes idle, then 5 writes and 5 reads | 10 execs | all succeeded; median 162 ms |

1,112 operations, no failures, no timeouts, no stall. The earlier stalls
therefore remain **unexplained and unreproduced**, in roughly 2,000 operations
since. This does not show the cause is gone: the original stall followed 18
iterations of a two-microVM loop after a clean start, a pattern phase B repeated
for 400 iterations without effect. Start time under concurrent load (median
9.9 s) was higher than the 6.8 to 7.2 s measured on an otherwise idle VM.

## Test errors worth knowing about

My own harness caused two false results before the data above: forced
cleanup left stale containerd state (`mkdir ...: file exists`), and a `pkill -f`
pattern matched its own shell. Both are recorded because they also show that
partial cleanup of Kata state is easy to get wrong, which supports D-23
(journaled, reconciling `sandboxd`).

## Decision (OQ-15, owner, 2026-11-18)

The owner chose `auto`, with atomic-rename writes in the sync tool and the 1 s
window stated in the release notes. The 100,000-file `git status` measurement
(`never` about 2× slower than `auto`) supports the choice. The data behind it:

The virtio-fs cache mode trades correctness for speed: `auto` is fast and has a
1 s stale-size window; `never` is coherent and about 19× slower on metadata.
Neither is acceptable unqualified for §5.13 (shared tree by default). Options:
`auto` with the window documented and the sync tool writing atomically; `never`
only when a second session joins a tree (it is fixed per microVM, so this
needs restarts); or `never` everywhere if the 100k-file measurement is
acceptable.
