# S6 — Fleet capability check

**Status:** partial. Two machines tested at the KVM level: the Apple M6 below and a
Linux x86_64 host (see "Linux host" below). On the M6 nested KVM works, and a Kata microVM
with Cloud Hypervisor boots, runs a workload on a virtio-fs workspace, and
tears down cleanly (details in `S1.md`). Reaching a gateway from the microVM
(the last part of §5.2.3 check 3) has not been tested.

## Environment

| | |
|---|---|
| Date | 2026-11-18 |
| Machine | MacBook Pro, Apple M6, 12 cores, 32 GiB |
| OS | macOS 27.3 (build 26C5035r) |
| Lima | 2.3.0 (`/opt/homebrew/bin/limactl`) |
| Guest | Ubuntu 24.04 cloud image, arm64, kernel 6.8.0-147-generic |
| Host `kern.hv_support` | 1 |

## What was run

1. Throwaway instance `v3-spike`: `vmType: vz`, `nestedVirtualization: true`,
   `mounts: []`, 4 CPUs, 8 GiB, 20 GiB disk, containerd off.
2. In the guest: `ls -l /dev/kvm` and `dmesg | grep -i kvm`.
3. Functional check: install QEMU 8.2.2 in the guest (after `apt-get update`;
   the first install failed with stale package URLs), then boot the guest's
   own kernel nested:
   `qemu-system-aarch64 -M virt -accel kvm -cpu host -m 512 -smp 2 -nographic -kernel /tmp/vmlinuz -append "console=ttyAMA0 panic=-1 root=/dev/vda"`.

## Observed

- `/dev/kvm` present in the guest (`crw-rw---- root kvm`); the guest kernel
  logs `kvm [1]: IPA Size Limit: 40 bits`, GICv3 and vgic initialisation.
- The nested guest kernel booted under KVM, printed
  `smccc: KVM: hypervisor services detected`, and stopped at the expected
  `Kernel panic - not syncing: VFS: Unable to mount root fs` (no root disk was
  supplied). `timeout` ended the run after its panic-reboot loop.

## Linux host (2026-11-19)

| | |
|---|---|
| Machine | AMD Ryzen 7 7840HS (16 threads, AMD-V), 30 GiB |
| OS | AlmaLinux 10.2, kernel 6.12.0-211.74.2.el10_2.x86_64; SELinux as shipped |
| Host nested KVM | `/sys/module/kvm_amd/parameters/nested` = 1 (on by default); `/dev/kvm` mode 0666, group `kvm` |
| Lima | 2.3.0 from Homebrew (`/home/linuxbrew/.linuxbrew/bin/limactl`) |
| QEMU used by Lima | **11.1.3 from Homebrew**, pulled in as a dependency of the `lima` formula, not the distro's `qemu-kvm` 10.1.0-28 (installed at `/usr/libexec/qemu-kvm`, and not on `PATH` as `qemu-system-x86_64`) |
| Guest | Ubuntu 24.04 cloud image (release 20261017), x86_64, kernel 6.8.0-147-generic |

**What was run**
1. Throwaway instance `v3-spike`: `limactl create --vm-type qemu --arch x86_64 --cpus 4
   --memory 8 --disk 20 --set '.mounts = [] | .plain = true' template:ubuntu-24.04`. Lima's
   `nestedVirtualization` key applies only to vz; on qemu, nesting comes from the host's
   `kvm_amd nested=1` and the `-cpu host` and `-machine q35,accel=kvm` arguments Lima passed
   (checked on the running QEMU's command line). The VM was ready about 13 s after
   `limactl start`.
2. In the guest: `ls -l /dev/kvm`, `dmesg | grep -i kvm`, `lscpu`.
3. Functional check: install QEMU 8.2.2 in the guest (`qemu-system-x86`), then boot the
   guest's own kernel nested:
   `qemu-system-x86_64 -accel kvm -cpu host -m 512 -smp 2 -nographic -no-reboot -kernel
   /tmp/vmlinuz -append "console=ttyS0 panic=-1 root=/dev/vda"`.

**Observed**
- `/dev/kvm` present in the guest (`crw-rw---- root kvm`). The `svm` flag is exposed on all 4
  vCPUs, and `lscpu` reports AMD-V with hypervisor vendor KVM.
- The nested kernel logged `Hypervisor detected: KVM` and `Booting paravirtualized kernel on
  KVM`, then stopped at the expected `Kernel panic - not syncing: VFS: Unable to mount root fs`
  1.3 s after boot. With `-no-reboot` QEMU then exited 0. `-accel kvm` was given with no
  fallback, so it could not have run under TCG.

**Result:** §5.2.3 checks 1 and 2 pass on this host. Check 3 (the Kata canary) is S1's
Linux run, not yet done.

**Findings for the design**
- **Homebrew's Lima brings its own QEMU on Linux.** A RHEL-family host that installs Lima
  from Homebrew runs Homebrew's QEMU, not the distro's KVM build.
- **Lima does not find the RHEL QEMU binary on its own.** In a second throwaway VM, with
  `PATH` limited to `/usr/bin:/bin:/usr/sbin:/sbin`, `limactl start` failed at once:
  `exec: "qemu-system-x86_64": executable file not found in $PATH`. Lima 2.3.0 has no
  fallback to `/usr/libexec/qemu-kvm`. With a symlink named `qemu-system-x86_64` pointing at
  `/usr/libexec/qemu-kvm` placed first on `PATH`, the same VM booted in about 15 s on the
  distro QEMU 10.1.0-28, with `-cpu host`, `accel=kvm`, and the distro's UEFI firmware, which
  Lima found by itself (`/usr/share/edk2/ovmf/OVMF_CODE.fd`); `/dev/kvm` and `svm` were
  present in the guest. So the distro build works once Lima can find it by name. The `.rpm`
  packaging in §10 must either ship that link (or set Lima's QEMU path) or depend on a QEMU
  that provides `qemu-system-x86_64`; a plain `dnf install qemu-kvm` is not enough.
- **Lima's default disk is 100 GiB.** A `limactl create` without `--disk` gave a 100 GiB
  sparse disk, against 20 GiB here.
- **No vz-only settings.** `nestedVirtualization` and `networkOpts.hostLoopback` are vz-only.
  Nesting needed no setting here. Host reach under qemu (S7) has to be tested separately.
