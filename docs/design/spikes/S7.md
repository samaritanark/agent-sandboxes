# S7 — Host-reach control per driver

**Status:** partial. Lima's own behaviour on `lima-vz` was measured. The
`sandbox netd` option, IPv6, and VM-root tampering were not tested, so the exit
criteria are not met.

## Environment

Apple M6, macOS 27.3, Lima 2.3.0, `vmType: vz`, throwaway instance `v3-spike`
(Ubuntu 24.04 arm64 guest, no mounts). Host LAN address 192.168.1.178. Test
listeners were `python3 -m http.server` run from an empty directory and killed
after each run.

## F4 — does Lima publish guest loopback listeners on the host?

Method: in the guest, `python3 -m http.server 18765 --bind 127.0.0.1`; from the
host, `curl http://127.0.0.1:18765/` and `lsof -iTCP:18765 -sTCP:LISTEN`.

| Config | Host `127.0.0.1:18765` |
|---|---|
| Defaults (guest agent running) | **HTTP 200**; the host listener belongs to the `limactl` process |
| `plain: true` | Not reachable; nothing listening on the host |

The installed 2.3.0 `default.yaml` documents the fallback rule ("Lima
internally appends this fallback rule ... guestIP 127.0.0.1 ... hostIP
127.0.0.1") and says plain mode ignores port-forwarding properties and does not
run the guest agent. **Review finding F4 is confirmed, and `plain: true` closes
it on this version.** Observed side effects of plain mode: `limactl shell`
(SSH) and `limactl start` readiness still work.

## Host reach from the guest (`networkOpts.hostLoopback`, new in Lima 2.3, vz only)

Method: host listeners on `127.0.0.1:18766` and `0.0.0.0:18767`; from the
guest, `curl` to `192.168.5.2` (`host.lima.internal`) and to the host LAN
address.

| Target from guest | `hostLoopback` default (true) | `hostLoopback: false` |
|---|---|---|
| `192.168.5.2:18766` (host loopback-only listener) | HTTP 200 | unreachable |
| `192.168.5.2:18767` (host all-interfaces listener) | HTTP 200 | unreachable |
| `192.168.1.178:18767` (same listener via host LAN IP) | HTTP 200 | unreachable |

With `hostLoopback: false`, outbound NAT still worked (`https://example.com/`
returned HTTP 200, name resolution worked). Both `plain: true` and
`hostLoopback: false` were in force for the second run.

Lima's own comment says the option "does not restrict the host's other
addresses: a host service bound to all interfaces is still reachable through
the host's LAN IP". **That did not reproduce here** (the LAN-IP case was
blocked). The comment and this single measurement disagree, so do not rely on
either until the cause is known (for example a hairpin effect of the NAT, or a
difference between listener types).

## What Lima's default network is (read from the host-agent log and binary)

On `lima-vz` the VM's default NIC is **already a host-side userspace stack**:
- the host agent's log (`ha.stderr.log`) shows `gvproxy API request` entries
  (`/services/dhcp/leases`, `/services/dns/add`), DNS listeners on host
  loopback, and `using usernet forwarder`;
- the `limactl` binary links `containers/gvisor-tap-vsock` packages
  (`services/dhcp`, `services/dns`, `services/forwarder`, `client`, `sshclient`);
- the guest's gateway and DNS are `192.168.5.2` and Lima's `192.168.5.x`
  addressing, which is gvisor-tap-vsock's default.

Consequences for D-31 and §5.2.6:
- The "owner that outlives the `sandbox` CLI" already exists for `lima-vz`: the
  Lima host agent is a detached process that lives as long as the VM, and it
  holds the stack. Option 1 in D-31 is therefore the stock behaviour, and its
  one policy control is `hostLoopback`.
- What stock Lima does not offer is **per-endpoint scoping**: `hostLoopback` is
  all or nothing. A declared Tier 3 host endpoint (for example a local k3d API
  on host loopback) would need the VM to run with `hostLoopback: true`, which
  exposes every host loopback port to VM root while it is set. VPN-routed
  destinations are unaffected, because they leave through the host's routing
  table.
- Making `sandbox netd` the VM's **only** NIC is not available through Lima's
  configuration as far as I found: `networks:` adds interfaces (`lima:`,
  `socket:` for `socket_vmnet`, `vzNAT`), and the template describes the built-in
  network as always present. I did not test removing it. Lima 2.3 ships
  separate driver executables under `libexec/lima` (for example
  `lima-driver-krunkit`); whether an external driver can attach a different NIC
  was not investigated, and a vfkit-based driver of our own (as podman machine
  does with gvproxy) would be the other route.
- Not tested here: probing what else answers on the gateway address
  `192.168.5.2` (beyond DNS and DHCP), and the gvproxy API socket's exposure.

## Implication for the design

`hostLoopback: false` is a host-side (vz) control that VM root cannot change
from inside the guest, which makes it a candidate native control for `lima-vz`
(§5.2.6 alternative). By itself it cannot scope declared Tier 3 endpoints, since
it blocks all host reach, and it does not exist on `lima-qemu` or Hyper-V. The
`netd` design in D-31 stays the primary option until the remaining rows are
tested.

## Update 2026-11-25: the LAN-address path is open on lima-vz

`sandbox doctor` (the host binary's check 4 of design 5.2.3) was run against the v3 appliance on
the same M6 (macOS 27.3, Lima 2.3.0, `vmType: vz`, `plain: true`, `hostLoopback: false`). The host
binary listened on all interfaces on a random port; VM root tried each target with bash's
`/dev/tcp` and a three-second timeout.

| Target from the guest | Result |
|---|---|
| `192.168.5.2` (`host.lima.internal`) | blocked |
| the host's IPv6 ULA address | blocked |
| the host's LAN address `192.168.1.178` | **reachable**: the host listener accepted the connection, from the host's own address |

So Lima's documented caveat (hostLoopback "does not restrict the host's other addresses") holds:
the earlier run above, where LAN-address reach did not reproduce, did not cover a listener bound
to all interfaces. The source address shows the user-mode NAT on the host dialling out as a host
process. Consequence: on lima-vz, `hostLoopback: false` does not meet 5.2.6's default (no host
reach); any host service bound to all interfaces is open to VM root. A host-side filter in the
NAT (`sandbox netd`, D-31) or an equivalent per-destination control is needed, not just
defense in depth. `sandbox doctor` now fails on this and is the regression check (N-02).
